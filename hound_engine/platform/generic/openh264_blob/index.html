Runtime Cisco-blob state + verified load backing openh264. Which codec implementation backs this process: the runtime-supplied Cisco libopenh264 binary — install/enable state, blob-path resolution, and the SHA-256-verified load every codec construction goes through. See [super::openh264] for the licensing rationale (the blob is downloaded onto the user’s device at first run; no build of ours contains an H.264 codec).

Constants§

BLOB_PATH_ENV 🔒
Escape hatch naming an already-downloaded Cisco binary, for contexts with no app to run the download: CI jobs (the blob comes from the http:openh264 mise tool), benches, and offline dev. Same posture as HOUND_APP_ROLE / HOUND_ZEROCOPY_VIDEO. Consulted only when nothing was installed explicitly.

Statics§

BLOB_ENABLED 🔒
The user’s kill switch for Cisco’s binary codec (openh264 BINARY_LICENSE conditions 2–4 require one). While false the installed blob is invisible to both the codec constructors and sw_h264_available. There is no other software H.264 to fall back to, so off means none at all — which is exactly the user’s stated choice.
BLOB_PATH 🔒
Filesystem path of Cisco’s libopenh264 binary, installed once per process by install_blob. A OnceLock (not a parameter) deliberately: [crate::Engine] is a Copy ZST constructed ad hoc at ~30 call sites, so threading a codec path through the facade would touch every one of them for a process-global fact.

Functions§

active_blob_path 🔒
The Cisco binary this process should use right now, if any: the explicitly installed path, else BLOB_PATH_ENV. None when the user turned the codec off, when nothing is installed, or when the named file has since vanished.
api 🔒
The openh264 API backing a new encoder/decoder: the Cisco binary, or a typed error naming the one thing that fixes it. There is no compiled-in codec to fall back to — by design, since only Cisco’s own binary carries their patent grant — so “not downloaded yet” is a legitimate state, not a bug.
blob_enabled 🔒
Whether Cisco’s binary codec is currently permitted (the settings toggle).
install_blob 🔒
Install Cisco’s libopenh264 binary at path for the rest of the process.
load_blob 🔒
Load (and SHA-256-verify) the Cisco binary at path.
resolve_env_blob 🔒
Resolve BLOB_PATH_ENV, which may name either the library itself or a directory containing it.
set_blob_enabled 🔒
Turn Cisco’s binary codec on/off at runtime (the settings toggle). Off also means “do not use a blob that is already installed” — the switch has to be effective, not merely advisory.
sw_h264_available 🔒
Whether this process can build a SW H.264 codec right now — the honest input to encode_caps/decode_caps. False when the blob has not landed yet (or the user disabled it), where advertising H.264 would promise peers a codec we cannot construct.
