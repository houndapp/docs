§Mixed-playout audio bus — one device stream + one coherent AEC reference

All remote peers play through ONE mixed output stream. Echo cancellation requires it: Apm::process_render must be fed the one coherent stream the speaker actually plays — interleaving independent per-peer render references corrupts AEC3’s canceller for any N>1. A single mixed playout makes the render reference exact for any N by construction, and halves the device handles (one stream per call, not one per peer).

§The tick model (PULL-based: the RT thread is the sole release clock)

One dedicated playback thread per call owns the single CpalPlayback. It ticks on a wall-clock 10 ms cadence (the APM chunk size, MIX_CHUNK_SAMPLES) — driven by the OUTPUT side, never by peer frame arrival, because the cpal ring absorbs the jitter between the tick and the DAC. On each tick the bus, for EACH registered producer:

  1. pops every due frame from that peer’s jitter buffer on its OWN real-time clock — playout.pop_due_into(clock.now() + lookahead, …) — appending the released PCM to the slot’s sample carry-queue, then drains up to MIX_CHUNK_SAMPLES from the carry,
  2. sums the producers sample-for-sample in i32, soft-limits the sum (AGC2’s limiter, as libwebrtc’s frame_combiner.cc does) and converts to i16 with a saturating backstop — so N loud peers cost ~a dB of gain rather than a flat-topped, broadband-distorted mix,
  3. pushes the mixed chunk to the CpalPlayback ring, and
  4. feeds what the ring ACCEPTED to Apm::process_render (the single coherent reference — only what the speaker actually emits belongs in it).

Usually that is exactly one chunk per tick, but the count is REGULATED by the device ring’s depth (chunks_for_tick): the DAC drains on its own crystal and this thread refills on a software clock, so an open-loop one-chunk-per-tick push walks the ring either dry (continuous dropouts) or full (latency pinned at the ring depth, overproduction silently discarded). Feeding back off the depth also makes a scheduling stall recoverable — the drained cushion is replayed instead of being spent for the rest of the call.

§Why pull, not push

A push design — a per-peer pump task (a normal async task) calling pop_due_into and PUSHING samples into the slot for this RT thread to drain — puts a second, non-real-time scheduler on the release path: under video-encode load the pump gets descheduled, feeds its slot late, and the RT drain finds the slot short — an audible per-peer gap (mix_starves) with the device ring still full (output_underruns == 0). No slot lead or cushion can fix that, because the producer’s timing is the variable. Pull — the RT thread is the ONLY thing that calls pop_due_into, on its own steady clock — removes that scheduler from the release path entirely. The pump’s sole job is to FILL the jitter buffer (network-paced; its scheduling never affects playout), and the jitter buffer IS the cushion that absorbs the pump’s arrival jitter. Both push (pump) and pop (this thread) read the same Copy [CaptureClock], so the buffer’s sender→local timeline mapping is consistent across the two threads.

§How the tick is paced

The cadence comes from an ABSOLUTE deadline schedule (TickPacer): tick n is due at epoch + n × MIX_TICK, never at now + MIX_TICK, so a late wake is not folded into the next deadline and the grid cannot drift. Each tick waits coarsely to within SPIN_MARGIN of its deadline and then busy-waits the remainder, because the coarse wait only guarantees a LOWER bound on the delay: its overshoot is the OS timer granularity, which on Windows is 15.6 ms by default — three tick periods over the ask, landing straight in the tick-late histogram (and, downstream, in the receiver’s decode-budget limitation signal). The coarse wait is therefore per-platform (CoarseWait): a plain sleep off Windows, and on Windows a high-resolution waitable timer whose ~0.5 ms accuracy is independent of that 15.6 ms clock.

When zero producers are registered the bus STILL ticks (pushing silence), so the device stream and the AEC reference stay warm for the whole call — AEC3’s delay/echo state does not have to re-converge each time the room goes briefly quiet or the last peer’s pipeline is mid-rebuild.

§Registration + bounds

A per-peer pipeline, instead of owning a playback thread, registers a BusProducer and PUSHES its decoded, timestamped PCM into the slot’s jitter buffer via BusProducer::push (which also folds the arrival into the slot’s AdaptiveJitter and reports back the depth/jitter for stats). The RT thread pulls from that buffer. The jitter buffer is bounded (drop-oldest at its frame cap) and the sample carry-queue is bounded to ~100 ms (SLOT_CAPACITY_SAMPLES) drop-oldest, so one stalled or runaway peer can never grow the bus’s memory. Dropping a BusProducer (its pipeline torn down / aborted) unregisters its slot from the bus, so a left peer stops contributing to the mix with no explicit teardown call.

§Hot-swap / vanish / reopen

The bus thread owns the speaker DeviceChoice hot-swap, the vanished-device fallback (handled inside CpalPlayback::start), and the reopen backoff — in ONE place targeting the ONE stream. call_set_speaker nudges the shared watch sender; the bus thread re-opens the single device in place without disturbing the mix.

Only a stream that actually DIED takes the immediate reopen. Everything the backend reports on a still-live stream — an automatic reroute, and the demoted quality faults (cpal Xrun / RealtimeDenied) — rides one debounce (RouteSettle) that collapses a burst into a single re-sync, because each reopen is itself a blocking device open on this real-time thread plus a fresh cushion prefill.

Being the only party that sees a recovery’s OUTCOME, this thread also owns the decision to report one: a stream error is logged at warn where it happens and only becomes an error! (a Sentry event) if playout is still down after the whole reopen ladder has run — see OutputHealth.

§!Send discipline

cpal::Stream is !Send on CoreAudio, so the CpalPlayback is constructed, driven, and dropped on the bus’s own thread and never crosses a thread boundary. Producers (Send/Sync) only ever touch the bounded slot queues.

§Decoupling

This module is deliberately free of session-specific types: it takes raw mono i16 PCM (&[i16]) in and plain handles out. The only audio dependencies are Apm (the render-reference sink) and CpalPlayback (the device), both behind narrow calls.

BusProducer
A handle a per-peer pipeline holds to push its decoded PCM into the mix. Pushing is non-blocking and bounded (the jitter buffer + the ~100 ms carry are both drop-oldest). Dropping the handle unregisters the producer’s slot from the bus (so a torn-down peer stops contributing with no explicit call) — the Drop-safe teardown the ghost discipline requires.
PlayoutBus
The mixed-playout bus for one call. Owns the dedicated playback thread (which owns the single CpalPlayback and runs the 10 ms mix tick) and the producer registry. Per-peer pipelines register a BusProducer and push their due PCM into it; the bus sums them, feeds the mixed chunk to the APM render reference once, and plays it.
PushStatus
What a BusProducer::push reports back so the caller can surface per-peer audio-health stats without a second lock — everything the debug report needs to attribute a glitch to the jitter-buffer stage.
Registry 🔒
The set of live producer slots, shared between the bus thread (which iterates it every tick) and register/unregister (called from the async subscribe loop as peers come and go). A std::sync::Mutex is right: the critical section is a HashMap insert/remove or a cheap clone of the slot Arcs, never held across IO.

Constants§

MAX_CHUNKS_PER_TICK 🔒
Ceiling on chunks emitted in ONE tick while catching up. Each chunk is a full mix + AEC render pass, so an unbounded catch-up would turn a stall into a CPU spike on the RT thread. 4 (40 ms) restores the whole cushion from a dry ring in a single tick, which is the worst case the depth signal can report.
MIX_CHUNK_SAMPLES
Samples in one mix tick: 10 ms @ 48 kHz mono = 480. Identical to the APM’s native chunk (APM_FRAME_SAMPLES) so the mixed chunk feeds process_render as exactly one block, and the tick cadence matches the canceller’s frame size.
MIX_DUE_SCRATCH_FRAMES 🔒
Initial capacity of the bus thread’s per-tick release scratch (MixScratch::due). A steady 10 ms tick releases 0 or 1 of a peer’s 20 ms frames. The headroom is for the case that actually produces a burst: a DESCHEDULED tick, where everything that came due while the thread was off-CPU is released at once (bounded by the jitter buffer’s max_frames, 256). Pre-sizing keeps the common tick off the allocator entirely; a long stall still grows the Vec a handful of times, once, and then never again.
MIX_PULL_LOOKAHEAD_US 🔒
How far PAST strictly-due the RT thread pops each tick: exactly one MIX_TICK (10 ms). A 20 ms audio frame spans two 10 ms ticks, so its due-instant lands between ticks for some phase offsets; a one-tick lookahead releases the next frame into the carry-queue before the carry can bottom out, so the slot always has a full chunk to drain regardless of how the frame-due phase aligns to the tick grid. Because the RT thread (not the pump) owns this read, the lookahead is immune to producer scheduling — it just smooths the frame/tick phase. Net latency is unchanged: a frame released lookahead early simply waits that long in the carry-queue instead of the jitter buffer.
MIX_TICK 🔒
The wall-clock period the bus thread ticks at: 10 ms, matching MIX_CHUNK_SAMPLES at 48 kHz. Output-side cadence — the cpal ring absorbs the difference between this and the DAC’s real pull timing.
MIX_TICK_MS 🔒
MIX_TICK in milliseconds — the chunk duration the output cushion is counted in.
NO_PEER_TAG
A sentinel peer_tag for a producer registered without attribution (the plain PlayoutBus::register) or a bus-global event (a late tick) — the glitch is recorded but not tied to a specific peer.
SLOT_CAPACITY_SAMPLES 🔒
Per-producer slot bound: ~100 ms of 48 kHz mono audio (4800 samples). A drop-oldest policy keeps a stalled/runaway peer from growing the bus’s memory; 100 ms is ~5 mix chunks of slack, enough to ride out a scheduling hiccup without unbounded growth.
SLOT_POOL_CAP 🔒
Recycled PCM buffers per slot: the pump allocates a frame’s samples in Slot::push and the bus thread frees them after draining into the carry, so a small free-list keeps ~50 malloc/free per second per peer off the RT tick. Bounded (a runaway pump can’t grow it) and best-effort (the RT side only try_locks).
SPIN_MARGIN 🔒
How long before a tick’s deadline TickPacer stops sleeping and busy-waits.
SPIN_YIELD_FLOOR 🔒
Inside SPIN_MARGIN, the point at which the pacer stops offering the CPU to other threads and only spins. Above the floor a yield_now per iteration keeps the busy wait from starving a runnable sibling on a core-starved box (this thread is RT-priority — it can and will win the CPU outright); below it, yield_now’s own syscall cost is on the order of the remaining wait, so the cheaper spin_loop hint carries the last stretch to the deadline.
TICK_GLITCH_CAPACITY 🔒
Initial capacity of the bus thread’s per-tick glitch buffer. One tick can record at most one underflow per registered slot plus a late-tick event; 8 covers any realistic call (mic + screen audio per peer) without the allocator ever appearing on the RT path — least of all on the already-late tick that is doing the recording.
TICK_LATE_GLITCH_US 🔒
A mix tick this late (µs) or more is recorded as a GlitchKind::LateTick. Half a tick (5 ms) — below this is ordinary scheduler noise the output cushion absorbs; above it the RT feeder genuinely slipped and the device ring risks draining.
