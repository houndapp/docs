§Device-outage escalation — report the failure that did NOT recover

Every audio device loop in the stack recovers from a dead stream by reopening: the mix bus’s output sink (super::mix) and the client’s mic capture loop both drop the endpoint and re-open it on a backoff. The device errors that trigger that are overwhelmingly transient and self-healing — a USB headset unplugged, a suspend/resume, a PipeWire node restarted under the stream, an ALSA EIO — and the reopen has fixed them within a tick.

So the thing worth an operator EVENT is not the stream error. It is an outage that outlives the recovery: no device for N seconds across M failed reopens. Reporting at the error callback instead files an issue for every successfully-recovered hiccup while a genuinely-down device (whose reopens quietly fail forever) produces nothing at all.

This module is that latch. It owns no clock — the caller passes Instants — so the policy is unit-tested rather than inferred from a live device, and the real-time mix thread can drive it from the Instant it already sampled.

How long an audio endpoint may stay down before the outage is escalated from a warn! (recovery in progress) to an error! (recovery is not working — the Sentry bridge promotes first-party error! to an event).
