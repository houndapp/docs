Message search: POST /search.

One endpoint, two engines. The client sends a parsed [hound_search::Query] — never the raw text — and this module compiles it to whichever dialect the connection speaks: a PGroonga full-text match on Postgres, an FTS5 match on SQLite (see sql). Everything else about the query — authors, mentions, content facets, date bounds, the keyset — is identical SQL on both.

§The two halves

  1. Which spaces, resolved from the request’s scope and the caller’s permissions (Api::searchable_spaces). The resulting id list is a space_id IN (…) predicate, so a space the caller cannot read is structurally absent from the search rather than filtered out of its results. in: only ever narrows that list.
  2. Which messages, a single statement returning (id, score) pairs, then a batch hydration into the same shape the message history endpoint returns (hydrate).

§Ordering and paging

Newest is id DESC — message ids are UUIDv7, so that is send order and it is the primary key. Relevant is score DESC, id DESC. Both page by keyset (cursor) rather than offset: a search re-run against a table that has grown must not repeat or skip a row at a page boundary. There is no total count; the client pages until next_cursor is null.

Relevance needs something to score against, so a query with no positive text term is sorted newest-first whatever the request asked for — on SQLite there is no FTS row to take a bm25 from at all.
