Compiling a [hound_search::Query] to one statement.

The only raw SQL in the backend, and it is raw because neither text engine has a sea_query expression: PGroonga’s &@ and FTS5’s MATCH are operators against index-backed pseudo-columns. Everything else is written by hand alongside them rather than half in the query builder.

§The two dialects

Postgres matches per term — search_text &@ $term, one predicate each, NOT (…) for a negation — and takes its relevance from pgroonga_score(tableoid, ctid).

SQLite has one MATCH string for the whole query, because FTS5 admits a single match expression per table reference: positives joined by AND, each negation appended as NOT "…". With no positive term the polarity flips and the whole thing becomes a rowid NOT IN of the negations OR-ed together. Relevance is -bm25(…) (FTS5’s bm25 is negative, best-first), which needs the FTS table joined rather than used as a subquery.

§Terms are phrases

A term’s words must appear adjacent, quoted or not. That is already what &@ does with a multi-token argument under a position-recording tokenizer, and what a quoted FTS5 string does, so the two agree without either side being special-cased. Term::phrase therefore does not change the SQL — it is a fact about how the user wrote it, which the UI’s highlighting uses.

§Nothing is post-filtered

Every constraint, permissions included, is a predicate here. A row this statement returns is a row the caller may read, so hydration never has to drop one — and a bug in hydration cannot leak a message.
