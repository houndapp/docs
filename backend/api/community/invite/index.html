Module invite 

Source
Expand description

Community invites: minting shareable codes, and redeeming one.

An invite is a row that carries its own whole policy — an optional expiry, an optional seat count, and a revocation stamp. Its state is therefore derived on every read (InviteState::of) rather than stored, so nothing has to run for an expired invite to stop working.

The seat count is the one thing a derived read cannot enforce: two people holding the last seat both see “active”. Redemption closes that with a conditional UPDATE … WHERE uses < max_uses inside the joining transaction, so the database, not the handler, decides who got the seat — see Api::claim_invite_seat.

Minting and listing are community-scoped (ManageUsers); redemption is not, because a caller holding a code does not yet know which community it opens. Those two routes live under /invite (see router) and need only a session.

Constants§

CODE_ALPHABET 🔒
The code alphabet: Crockford base32 — the digits plus the letters, less I, L, O and U. The first three are dropped because they are the glyphs a human mis-copies as 1/0; U because dropping it is what keeps a random code from spelling something. Lookups uppercase the input, so a code read off a screen and typed in lowercase still resolves.
CODE_LEN 🔒
8 characters of a 32-symbol alphabet: 40 bits, ~1.1e12 codes. Short enough to read aloud, wide enough that guessing is not an attack.
MAX_EXPIRY_SECS 🔒
Inclusive bound on expires_in_secs. An invite that outlives the reason it was made is the one that leaks a community; 30 days is the longest a link stays useful without someone re-deciding.
MAX_MAX_USES 🔒
MINT_ATTEMPTS 🔒
How many fresh codes a mint will try before giving up. A collision needs two draws from 1.1e12 to match, so more than one attempt is already astronomically unlikely — the retry exists so a collision is a retry rather than a 500, not because it is expected.
MIN_MAX_USES 🔒
Inclusive bounds on max_uses. Zero would mint something already dead.
