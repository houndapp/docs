pub(crate) async fn can_manage_role( &self, user_id: Uuid, community_id: Uuid, role: &Model, ) -> DbResult<bool>

Whether user_id may edit role — rename it, delete it, change its grants, or change who is in it.

ManageRoles on its own is not enough, because a role can grant more than its editor holds: without this, anyone able to edit roles could add ManageCommunity to a role they are in and promote themselves. The rule is containment — you may only act on a role whose current grants you already hold yourself:

  1. An organiser may edit anything (they hold every permission).
  2. Otherwise the caller needs ManageRoles and the role’s current permission set must be a subset of their own effective set.
  3. @organisers is never editable this way: an organiser passes rule 1, and nobody else can hold “every permission” without being one.

Granting is the other half and is not decided here — see ApiError::PermissionNotHeld: a caller who may edit a role still cannot put a permission into it that they do not hold.

  2. Community default — the user’s community-level role_permission rows.

pub(crate) async fn provision_default_community( &self, name: &str, ) -> ApiResult<Option<Uuid>>

Provisions the instance’s initial default community at startup, so a freshly migrated database is usable the moment the first account registers: without it the instance sits unprovisioned until some client walks the POST /community → POST /instance/provision bootstrap by hand, and every user who registers before that lands in no community at all.

The community is created with the same layout POST /community produces (general/voice spaces, @organisers/@everyone roles). Who ends up in @organisers depends on what the database already holds:

  • Fresh database (the normal case) — nobody, because no user exists yet. The first account to register adopts the role, alongside the instance permissions it is granted (see Api::adopt_default_community_organiser).
  • Existing users — an instance that ran before it had a community, so registration’s auto-join never had anywhere to put them, and the one-shot first-user grant is already spent. Every one of those accounts is adopted: joined as a member and made an organiser. An instance whose every user predates its community has no other basis on which to single one out as its owner.

The second case fires at most once in an instance’s life (provisioning happens once), and only for accounts that predate the community — everyone registering afterwards joins as a plain member.

Idempotent, and safe to run concurrently on every replica of a rollout: the arbiter is the same conditional UPDATE ... WHERE provisioned = false that backs post_provision, executed inside the same transaction as the community insert — a replica that loses the race rolls its community back rather than leaving an orphan behind. Returns the new community’s id, or None when the instance was already provisioned (the overwhelmingly common case: every restart after the first).

pub(crate) async fn claim_first_user_grant( &self, conn: &impl ConnectionTrait, ) -> DbResult<bool>

Makes the space’s @everyone ACL agree with its is_private flag: a private space carries an explicit channels:view deny for the community’s @everyone role, a public one carries none.
