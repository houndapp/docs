Module media

The embed media proxy: the only path by which an embed’s images, poster frames and video reach a client.

§Why a proxy at all

A client that loaded og:image directly would hand its IP address — and, by the timing of the request, its presence — to whatever host the poster chose. A one-pixel og:image is a read receipt for a whole channel. The proxy makes every embed asset come from this deployment instead.

§Why it cannot be turned into a weapon

Three properties, together:

  • A closed URL set. The route addresses an embed row and a slot key (image-0, video, favicon); the remote URL is looked up, never supplied. There is no request shape that makes this fetch an arbitrary URL, which is what separates it from an open proxy.
  • A cache in front of the origin. A hot embed is served from memory, so a channel full of people opening the same message is one upstream fetch, not hundreds. Without this, an embed would be a bandwidth amplifier pointed at whatever it linked.
  • The same guard as the unfurl. The fetch runs through SafeFetcher, so a stored URL that now resolves to a private address is refused at fetch time, not merely at unfurl time.

§What it serves

Bytes whose type was confirmed by sniffing, under nosniff and a default-src 'none' CSP, with SVG refused outright — it is a script-bearing document wearing an image’s content type, and nothing in this client can render one anyway.

Constants§

ALLOWED_TYPES 🔒
The content types the proxy will serve. image/svg+xml is deliberately absent: an SVG is an XML document with script and external-reference capabilities, and no client here can render one regardless.
CACHE_MAX_BYTES 🔒
Server-side byte budget across all cached assets.
CACHE_MAX_ENTRIES 🔒
Most distinct assets held, independent of size — a cap on bookkeeping, not on memory (that is CACHE_MAX_BYTES).
CLIENT_CACHE_SECS 🔒
How long a client may reuse a proxied asset. Long: the URL is content- addressed by embed id, and an embed’s media never changes under it — a new unfurl mints a new row.
