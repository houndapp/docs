Known oEmbed providers, looked up by host.

§Why a registry, when discovery already exists

super::parse finds <link rel="alternate" type="application/json+oembed"> in the page, which works right up until it doesn’t:

  • the page a bot is served may not carry the link. A YouTube watch page for an unavailable or region-blocked video returns a shell whose only metadata is the site’s boilerplate — which unfurled to a card reading “- YouTube” over “Enjoy the videos and music you love…”, and is what prompted this;
  • the page fetch may fail outright, while the provider’s own endpoint answers perfectly well;
  • some providers publish an endpoint and simply never advertise it.

For a host we recognise, the endpoint is a fact we already know, so there is no reason to ask the page for permission to use it.

§What it buys, concretely

For YouTube, oEmbed is the ONLY source of provider_name (“YouTube”, not the host-derived “youtube.com”) and of the channel — author_name and author_url. Neither appears in the page’s Open Graph tags at all. It is not the source of the thumbnail: oEmbed offers hqdefault at 480×360 where og:image offers maxresdefault at 1280×720, which is why the precedence in super::build keeps Open Graph ahead of oEmbed for images.

§Adding one

Verify the endpoint answers before adding it — every entry here was checked against a live URL. Match on the REGISTRABLE host and let the suffix rule cover subdomains, so m.youtube.com and music.youtube.com arrive without separate entries.
