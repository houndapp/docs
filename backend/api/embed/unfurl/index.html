The unfurl pipeline: message text in, stored embeds and a realtime push out.

§Why this runs after the message is stored

Unfurling is a network round-trip against a stranger’s server. Doing it on the POST would put an eight-second worst case on every send containing a link, and would let a slow host pin a request worker. So the handler stores the message, answers, and spawns Api::spawn_unfurl; the previews arrive moments later as [ServerMessage::MessageEmbedsUpdated].

The cost of that choice is a visible two-step in the UI (message, then card), which is the same behaviour every other chat client has, and is why the realtime frame is a replacement list rather than an append — a client that misses it and re-reads history still converges.

§Which links get unfurled

The first [MAX_MESSAGE_EMBEDS] distinct http(s) URLs in the body, in the order they appear. Distinct by exact URL: the same link twice is one card.

§Failure is not an error

Nothing here can fail the message. Every outcome — refused by the guard, timed out, a 404, a page with no metadata — is recorded in the cache so it is not retried on every mention, and produces no card.
