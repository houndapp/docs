The IO shell around hound_realtime::Hub: connection registry, fanout, and the per-connection session loop both transports share.

§Locking

Two std Mutexes: the hub (routing state) and the connection mailboxes. Neither is ever held across an .await — every send onto a mailbox is try_send, which is synchronous. Fanout takes them in sequence (resolve targets under the hub lock, push under the conns lock); Realtime::admit is the one path that nests them, hub → conns, and nothing anywhere takes them in the other order. Both are acquired with poison recovery: a session task that panics must not take the realtime plane down with it, since every HTTP emit routes through the same locks.

§One task per connection

Each session is a single task owning its pipe, selecting between “a frame arrived”, “this connection has an outgoing message queued”, and — on a leg with no transport keep-alive — the liveness timers. Outgoing sends are awaited inline, so a slow client backs up only its own mailbox, never the fanout and never another connection.

§Bounds

Every resource a connection can consume is bounded before it is trusted: the per-user connection cap (MAX_CONNS_PER_USER) is reserved before the handshake, Hello must arrive inside SessionLimits::hello_deadline, the outbound mailbox is MAILBOX_CAPACITY deep and overflowing it is a disconnect, and a WebSocket that answers nothing is reaped. Teardown runs from a drop guard, so a panicking session cannot leak any of it.
