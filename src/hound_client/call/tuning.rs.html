13/// Per-peer jitter-buffer depth floor the adaptive jitter grows from. 80 ms buys
14/// headroom so a brief fill-thread scheduling hiccup under heavy video load can't
15/// drain the buffer before the next frame lands — defense in depth behind the RT
16/// audio runtime (which is what actually prevents starvation). The adaptive
17/// estimator still grows above this on a jittery link; the extra baseline latency
18/// is inaudible for conversation and buys a full Opus frame of slack.
19pub(super) const PLAYOUT_TARGET_US: i64 = 80_000;

23/// Camera publish bitrate ceiling.

26// the coalesced receiver cap (`hound_media::low_rung_for_cap` → `fit_encode_dims`
27// against `CAM_DIMS`), so a call rendered as a grid of thumbnails runs the low
28// encoder at 320×180@15 rather than 640×360@30. See `camera_tx.rs`'s low path.
29/// Screen-share publish geometry: capture is native, scaled to this 1080p-class
30/// cap preserving aspect (text stays legible without 4K uplink cost).
31pub(super) const SCREEN_MAX_W: u32 = 1920;
32pub(super) const SCREEN_MAX_H: u32 = 1080;
33pub(super) const SCREEN_FPS: Fps = Fps::new(30);
34// The LOW simulcast layer's screen geometry is NOT a constant either: the screen
35// ladder has two below-source rungs (`hound_media::SCREEN_LOW_RUNG` 360p15 and
36// `SCREEN_MID_RUNG` 720p30), and the capture thread inverts the coalesced receiver
37// cap into one of them and fits its PIXEL budget to the share's own aspect
38// (`policy::low_screen_dims`). A long-edge budget mispriced every non-16:9 share;
39// see that function. The screen ladder's rungs also differ in FRAME RATE, so the
40// low path's fps gate follows the settled rung — see `screen_tx.rs`'s low path.

42/// Camera keyframe cadence: a periodic IDR. Camera content changes wholesale
43/// (deltas are already large), so the periodic refresh is cheap insurance for
44/// loss recovery.
45pub(super) const CAM_KEYFRAME_CADENCE: KeyframeCadence = KeyframeCadence::MOTION;
46/// Screen keyframe cadence: IDRs **on demand only** (a subscriber's
47/// `RequestKeyframe` — sent at subscribe and re-sent by the receiver's
48/// awaiting-keyframe nag — or a PLI), plus a slow safety net. Screen content is
49/// mostly static, and a periodic IDR of an unchanged 1080p frame is pure
50/// redundancy — a short fixed cadence would dominate the data cost of a static
51/// share (hundreds of kbps for zero new information).
52/// `max_gop_frames = 900`: one GOP = one moq group, and moq-net evicts a group
53/// past 1024 objects (a fatal `CacheFull` for the drain) — 900 bounds the GOP
54/// safely under that cap even at sustained 60 fps (≈15 s), while the 60 s
55/// safety interval governs low-fps/static content (tiny groups).
56pub(super) const SCREEN_KEYFRAME_CADENCE: KeyframeCadence = KeyframeCadence::OnDemand {
57    safety_seconds: 60,
58    max_gop_frames: 900,
59};
60/// Screen publish bitrate seed — the initial encoder target before the BWE
61/// adaptation settles onto a ladder rung. Matches the 1080p30 SCREEN rung
62/// (~2.4 Mbps, see `screen_bitrate_bps`) — a screen-content target, NOT a
63/// camera-video one. A camera-grade seed (several Mbps) would saturate the shared
64/// QUIC connection before BWE reacts and starve audio/other video, while screen
65/// content (mostly static, text) looks crisp in H.265 at this rate. The BWE climbs
66/// from here if the link genuinely has headroom.
67pub(super) const SCREEN_BITRATE: Bitrate = Bitrate::kbps(2500);
68/// Mic Opus bitrate. 48 kbps mono fullband VOIP is effectively transparent for
69/// speech — Discord's 64 kbps default buys nothing audible over it on a mono mic
70/// track — while DTX + the publisher silence gate keep the idle cost near zero.
71/// Fixed for the call: audio is the "sacred" plane the send budget carves out
72/// first (`adapt.rs`), never the release valve; if audio ever must degrade under
73/// congestion, `OpusEncoder::set_bitrate` is the live lever (floor ~24 kbps).
74pub(super) const MIC_BITRATE: Bitrate = Bitrate::kbps(48);

76/// App-audio Opus bitrate for a shared window's audio. This is music/system
77/// audio, not a mic — encoded in `OpusProfile::Music` (general-audio) mode, so it
78/// needs a music-grade rate: speech-grade rates (~32 kbps) audibly crush music.
79/// 96 kbps mono is near-transparent for general audio.
80pub(super) const SCREEN_AUDIO_BITRATE: Bitrate = Bitrate::kbps(96);

84/// Re-emit the last screen frame at least this often (timestamp advanced) so a

87/// How long a changed window size must hold before the share restarts at the new
88/// geometry — one restart when a live drag-resize settles, not dozens.
89pub(super) const SCREEN_RESIZE_DEBOUNCE: std::time::Duration =
90    std::time::Duration::from_millis(700);
91/// Backoff the screen capture thread sleeps before signalling `Retry` after a
92/// transient capture error/panic — bounds the restart rate if the source keeps
93/// faulting immediately (the share restart itself paces it further).
94pub(super) const SCREEN_RETRY_BACKOFF: std::time::Duration = std::time::Duration::from_millis(500);
95/// How long a screen capture may run without EVER delivering a frame before the
96/// capture thread gives up and asks for a restart (`policy::first_frame_overdue`).
97/// A source that never produces frame #1 (Windows WGC can do this indefinitely)
98/// errs on nothing: no frames, no error, and the liveness probe still sees a live
99/// handle, so the loop would idle forever behind a black self-preview.
100///
101/// **5 s, deliberately longer than the engine's 3 s first-frame deadline at open.**
102/// The engine's own deadline is the precise instrument — it fires a typed open
103/// error the UI can route — and this backstop must not race ahead of it and turn a
104/// diagnosable open failure into an anonymous restart. This catches only what the
105/// engine-side deadline cannot see: a source that opens, satisfies the engine, and
106/// then never delivers.
107pub(super) const SCREEN_FIRST_FRAME_DEADLINE: std::time::Duration =
108    std::time::Duration::from_secs(5);

114/// moq-net delivery priorities — **audio must strictly outrank video on the wire** so
115/// a high-bitrate screenshare can never delay/burst the Opus streams on the SHARED
116/// QUIC connection (the "audio is sacred" wire guarantee).
117///
118/// ⚠️ COUNTERINTUITIVE VALUES — they compensate for an inversion in moq-net 0.1.9.
119/// moq-net ranks tracks by *descending* `track` value into a vec and hands quinn the
120/// vec **index** (`lite/priority.rs:138`, `new_priority = idx`, 0 = top rank). But
121/// quinn schedules the **largest** i32 first (`quinn-proto streams: BinaryHeap` max-
122/// heap). So a *smaller* `track` value → higher vec index → larger quinn priority →
123/// **served first**. Audio therefore takes the SMALLER value. If moq-net ever corrects
124/// the mapping, this inverts and audio would drop to lowest priority — the
125/// `audio_strictly_outranks_video_on_the_wire` guard test (`subscribe.rs`) fails
126/// loudly if that regression lands, and `moq-net` is pinned `=0.1.9` against it. Only
127/// the relative order matters (the value is used as an ordinal rank), not the
128/// magnitude. Used on BOTH subscribe (relay→us downlink) and publish (us→relay
129/// uplink), so it governs every audio/video contention point.
130///
131/// Two bands, not three — **no dominant-speaker band on the wire**, evaluated and
132/// rejected. A subscriber's priority is a SUBSCRIBE-time value in moq-lite (the
133/// SUBSCRIBE message carries it; there is no update message), so a dominance band
134/// can only be latched when a pipeline starts. That leaves two equally bad options:
135/// latch it and never revisit — every pipeline of a fresh establish is created
136/// before the ranker has any evidence, so the band is unreachable in steady state,
137/// while a pipeline that happens to start while its peer is dominant keeps the
138/// promotion forever and preempts the *actual* speaker — or resubscribe on every
139/// handover, which is exactly the shared-connection churn that has taken VOICE down
140/// (a wedged video sub churning the shared QUIC session). It also applies per PEER,
141/// so a dominant presenter's multi-Mbps screen share would outrank every camera in
142/// the call.
143///
144/// The P4 allocator (`hound_media::allocate`) has since landed and deliberately did
145/// NOT supply the bounded re-subscription path this was waiting on: it ranks tiles
146/// and emits RUNGS, so a ranking change moves a cap and nothing else — pinned by
147/// `subscribe::taking_the_floor_moves_the_cap_and_never_the_track`. It does move the
148/// layer axis (its deficit phase can demote a tile to `Hidden`), but only through
149/// `LayerHysteresis`'s debounce and dwell and only on a link that is genuinely short,
150/// which is not a per-handover path. So the premise here is unchanged, and P3's rung
151/// promotion (`hound_media::speaker_adjusted`) remains the whole quality lever.
152pub(super) const AUDIO_PRIORITY: u8 = 2;
153pub(super) const VIDEO_PRIORITY: u8 = 4;
154/// Heartbeat cadence (keeps the backend's voice-membership alive).
155pub(super) const HEARTBEAT_INTERVAL: std::time::Duration = std::time::Duration::from_secs(15);

161/// The per-peer broadcast path under the relay token's `space/{id}` scope.
162///
163/// `user_id` is the AUTHENTICATED identity the SFU always enforces the ingest
164/// half of this namespace against — for a SELF path it is this client's own
165/// logged-in user id; for a REMOTE path it must come from
166/// the control-plane roster's `PeerInfo::user_id` (never the realtime-derived
167/// [`PeerIdentities`] map, which is racy relative to the control plane). The
168/// trailing `peer.0` keeps same-user-multi-device paths distinct.
169pub(super) fn broadcast_path(space_id: Uuid, user_id: Uuid, peer: PeerId, track: &str) -> String {
170    format!("space/{space_id}/peer/{user_id}/{}/{track}", peer.0)
171}
