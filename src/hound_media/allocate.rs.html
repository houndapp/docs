1//! # Receiver-side total-budget video allocator
2//!
3//! Every other demand signal in this crate is **per track**: a tile prices its own
4//! rung ([`crate::layer::tile_quality_request`]), a subscription prices its own
5//! delivery ([`crate::downlink::DownlinkDemand`]), and the producer coalesces
6//! whatever arrives ([`crate::plan_layers`]). Nothing anywhere looks at the SUM.
7//! N tiles can each individually fit a link while their total overshoots it by a
8//! multiple — which is the shape of every large-call collapse: 31 tiles that each
9//! "only" want the source rung want 46 Mbps between them.
10//!
11//! This module is the missing cross-tile decision. [`allocate_video`] takes every
12//! visible remote tile's demand plus one total [`VideoBudget`] and hands each tile
13//! back a [`QualityRequest`] that is never richer than what it asked for and whose
14//! *sum* fits the budget. It is the receive-side twin of
15//! [`crate::send_budget::allocate_send_budget`], and it is what Zoom's ~2 Mbps
16//! 25-tile ceiling and LiveKit's `StreamAllocator` (rank tracks, distribute the
17//! estimated downlink, expose STABLE/DEFICIENT) both are.
18//!
19//! ## What it does NOT replace
20//!
21//! * the per-track delivery cap. [`crate::downlink::DownlinkDemand`] still folds in
22//!   afterwards via [`crate::most_constrained`] — the allocator budgets what this
23//!   receiver *asks for*, the downlink decider observes what it actually *gets*, and
24//!   the more constrained of the two wins. A budget cannot know a single track is
25//!   wedged, and a per-track observation cannot know 31 healthy tracks are 31 too many.
26//! * the producer's cross-receiver minimum. `plan_layers` still coalesces every
27//!   receiver's cap into ONE shared low layer, so a receiver asking for a richer rung
28//!   than its neighbours still does not get one. See the trade notes on `plan_layers`.
29//!
30//! ## Rung space, not bitrate space
31//!
32//! The output is a rung (or the source), never an interpolated bitrate. That is what
33//! keeps the allocator compatible with [`crate::layer::low_rung_for_cap`] on the
34//! producer side, and it is why re-running it every reconcile tick does not chatter:
35//! a budget that drifts by a few kbps lands on the same rung, so the downstream
36//! `LayerHysteresis` sees no change at all. A raw-bps allocator would re-request on
37//! every tick.
38//!
39//! Sans-IO: time enters only as an explicit `now_us`, and the allocation itself is a
40//! pure function of its inputs.

46/// One visible remote video tile, as the reconcile pass gathers it.
47///
48/// `demand` is the tile's **committed** demand — already speaker-modulated
49/// ([`crate::speaker_adjusted`]) and already past the seeded-tile escalation — so the
50/// allocator only ever removes quality, never adds it.
51#[derive(Debug, Clone, Copy, PartialEq, Eq)]
52pub struct TileRequest {
53    /// The remote peer this tile renders. The final, deterministic tiebreak.
54    pub peer: u32,
55    pub source: VideoSource,
56    /// What this tile asked for. A [`QualityRequest::Hidden`] demand passes straight
57    /// through: allocation is over VISIBLE tiles, and a tile nobody renders costs
58    /// nothing to leave alone.
59    pub demand: QualityRequest,
60    /// Position in the recent-speakers list (`0` = dominant), or `None` if unranked —
61    /// [`crate::SpeakerTiers::rank`].
62    pub rank: Option<usize>,
63    /// This peer's speaking tier. Only [`SpeakerTier::Silent`] is acted on as
64    /// *evidence* of unimportance; `Unknown` is a peer we know nothing about and
65    /// outranks it (the same two-tier trust rule as `speaker_adjusted`).
66    pub tier: SpeakerTier,
67    /// The tile's rendered size in **physical** pixels — the within-class tiebreak,
68    /// so the bigger of two equally-ranked tiles gets the richer rung.
69    pub tile_pixels: u64,
70}

72/// Priority class, cheapest ordinal = served first.
73///
74/// Screen shares outrank every camera (LiveKit ranks `screenshare > video` for the
75/// same reason: a share is content the call is *about*, and illegible shared text is
76/// a failure where a soft face is not). Cameras then sort by speaking rank, with
77/// unranked-but-unobserved ahead of observed-silent.
78const CLASS_SCREEN: u8 = 0;
79const CLASS_RANKED: u8 = 1;
80const CLASS_UNKNOWN: u8 = 2;
81const CLASS_SILENT: u8 = 3;
82
83/// The total order the allocator serves tiles in. Total and deterministic: every
84/// component is derived from the input, and the last one is unique, so the same
85/// input always produces the same output (no map iteration order reaches a decision).
86fn priority(t: &TileRequest) -> (u8, usize, std::cmp::Reverse<u64>, u32) {
87    let (class, rank) = match t.source {
88        VideoSource::Screen => (CLASS_SCREEN, 0),
89        // Silence is checked FIRST, so a peer still sitting in the MRU list that we
90        // have nonetheless watched be quiet for the whole long window sorts as
91        // silent. `Unknown` — no evidence either way — is never demoted past it.
92        VideoSource::Camera => match (t.tier, t.rank) {
93            (SpeakerTier::Silent, _) => (CLASS_SILENT, 0),
94            (_, Some(r)) => (CLASS_RANKED, r),
95            _ => (CLASS_UNKNOWN, 0),
96        },
97    };
98    (class, rank, std::cmp::Reverse(t.tile_pixels), t.peer)
99}

101/// What one allocated request costs against the budget. `Hidden` is free — it
102/// subscribes to nothing (`call::subscribe::pick_layer`).
103///
104/// Public because the budget is not only *spent* here: the reconcile loop prices the
105/// requests it actually committed and feeds the total back to
106/// [`VideoBudget::observe`] ([`BudgetObservation::committed_bps`]), and a second
107/// pricing table on that side of the seam could disagree with this one.
108pub fn request_bps(source: VideoSource, req: QualityRequest) -> u64 {
109    match req {
110        QualityRequest::Hidden(_) => 0,
111        QualityRequest::Capped(bps) => bps,
112        QualityRequest::Source => source_bps(source),
113    }
114}

119/// The ceiling a receiver that is **short of CPU** may spend a freed budget up to,
120/// as a cap a caller can fold into a demand with [`most_constrained`].
121///
122/// Once `call::policy::DecodeBudget` has cut below the platform ceiling, the shell
123/// folds this into every gathered tile's demand so the bitrate freed by hiding tiles
124/// cannot buy the survivors a rung whose DECODE is what the receiver just evidenced
125/// it cannot afford — see [`allocate_video`]'s "a cut must not fund an upgrade" note.
126///
127/// The cap is per-content, and deliberately not "the richest below-source rung":
128///
129/// * **Camera** — the richest below-source rung ([`crate::LOW_RUNG`], 640×360@20).
130///   Everything below the source is cheap to decode, so the only thing worth
131///   forbidding is the 720p30 source itself.
132/// * **Screen** — the *cheapest* rung ([`crate::SCREEN_LOW_RUNG`], 640×360@15), not
133///   the richest. [`crate::SCREEN_MID_RUNG`] is 1280×720@30: ~8× the decode work of
134///   the floor, and within a rounding error of the 1080p30 source's. Capping a
135///   CPU-crisis share at the ladder top would leave the clamp doing nothing at all
136///   for the single most expensive decode leg in the call, which is the one it was
137///   written for.
138///
139/// Both are named through [`low_rungs`], so this can never name a rung that ladder
140/// does not have.
141pub fn cpu_crisis_cap(source: VideoSource) -> QualityRequest {
142    let rungs = low_rungs(source);
143    let rung = match source {
144        VideoSource::Camera => *rungs
145            .last()
146            .expect("every source has at least one below-source rung"),
147        VideoSource::Screen => rungs[0],
148    };
149    QualityRequest::Capped(rung_bps(source, rung))
150}

152/// The tiles this receiver actually **serves**, as indices into `tiles`, in the
153/// priority order [`allocate_video`] serves them in. Tiles whose own demand is
154/// already `Hidden` are excluded (they subscribe to nothing); `decode_budget`
155/// truncates the rest to its `k` highest-priority entries.
156///
157/// This is THE definition of the served set, and it is public because the decode
158/// cut is not the only thing that has to agree with it. The reconcile loop prices
159/// its [`BudgetObservation`] — the demand ceiling the AIMD probes toward and the
160/// floor cost it seeds and dwells against — and both figures have to describe the
161/// tiles that will actually subscribe. Priced over the pre-cut set instead, a
162/// 32-tile gallery cut to 16 seeds its bandwidth budget with 32 floors and probes
163/// toward 32 demands: the controller would be sized for a receive leg that does not
164/// exist, and the join seed alone would hand out twice the budget the survivors can
165/// spend. One function, both callers, so the cut and the pricing cannot disagree.
166pub fn served_order(tiles: &[TileRequest], decode_budget: Option<usize>) -> Vec<usize> {
167    let mut order: Vec<usize> = (0..tiles.len())
168        .filter(|&i| !matches!(tiles[i].demand, QualityRequest::Hidden(_)))
169        .collect();
170    order.sort_by_key(|&i| priority(&tiles[i]));
171    if let Some(k) = decode_budget {
172        order.truncate(k);
173    }
174    order
175}

177/// The cheapest rung this content has — the floor every visible tile is guaranteed,
178/// clamped by the tile's own demand so the allocator can never hand out MORE than
179/// was asked for (a bandwidth-crushed `Capped(1)` stays at 1).
180fn floor(source: VideoSource, demand: QualityRequest) -> QualityRequest {
181    let cheapest = QualityRequest::Capped(rung_bps(source, low_rungs(source)[0]));
182    most_constrained(demand, cheapest)
183}

185/// The `Hidden` a demoted tile reports: not rendered, carrying the cap it *would*
186/// have asked for. That carried value is load-bearing — `plan_layers` uses it to size
187/// the shared low layer when every requester is hidden, which is what keeps the rung
188/// published so an un-demotion is a subscribe rather than a producer spin-up.
189fn hidden(source: VideoSource, demand: QualityRequest) -> QualityRequest {
190    let cheapest = rung_bps(source, low_rungs(source)[0]);
191    QualityRequest::Hidden(match demand {
192        // Never above the cheapest rung — a hidden tile that is the ONLY requester
193        // must size the shared layer at the floor, not at what its tile would have
194        // liked — and never above what the tile itself asked for.
195        QualityRequest::Capped(bps) | QualityRequest::Hidden(bps) => bps.min(cheapest),
196        QualityRequest::Source => cheapest,
197    })
198}

200/// The next richer option above `at`, never above `demand`. `None` = `at` is already
201/// everything this tile asked for.
202fn next_step(
203    source: VideoSource,
204    at: QualityRequest,
205    demand: QualityRequest,
206) -> Option<QualityRequest> {
207    let QualityRequest::Capped(now) = at else {
208        return None; // already on the source; nothing is richer
209    };
210    let next = low_rungs(source)
211        .iter()
212        .map(|r| QualityRequest::Capped(rung_bps(source, *r)))
213        .find(|s| price(source, *s) > now)
214        .or(Some(QualityRequest::Source))?;
215    // Never past what the tile asked for: the fold with its own demand is the
216    // ceiling, so a `Capped(420k)` demand stops at the low rung and never reaches
217    // `Source`.
218    (most_constrained(next, demand) == next).then_some(next)
219}

221/// Hand every visible tile the richest rung the **total** `budget_bps` can pay for,
222/// in priority order. Returns one [`QualityRequest`] per input, in input order.
223///
224/// Three phases, all in rung space:
225///
226/// 1. **Floor** — every visible tile is guaranteed its cheapest rung. A call does not
227///    silently drop people because the link is tight; it makes everyone small.
228/// 2. **Deficit** — if even the floor overruns the budget, tiles are demoted to
229///    `Hidden` from the BOTTOM of the priority order until it fits (never the
230///    top-priority tile: a receiver that can afford nothing still watches one thing).
231///    That is a layer-AXIS move, so the caller's existing layer-switch debounce
232///    (`call::policy::LayerHysteresis`) absorbs a transient dip rather than letting it
233///    blank tiles.
234/// 3. **Upgrade** — the remaining budget buys single-rung steps, CHEAPEST FIRST.
235///
236/// `decode_budget` caps the number of tiles that may hold a decoder at all,
237/// independent of bitrate — a receiver can be CPU-bound long before it is
238/// bandwidth-bound. Applied first, since it decides the tile SET the other two
239/// phases work over.
240///
241/// The shipped client always passes a number: `call::policy::DecodeBudget` starts
242/// it at the platform's static decode-session ceiling
243/// (`hound_engine::api::Engine::decode_session_budget` — 16 on every HW decoder,
244/// a thread-count prior on the software one) and halves it against RT audio-mix
245/// lateness, so a receiver sheds decoders to keep the audio thread scheduled. The
246/// ceiling reaches this function on the very first pass, before any evidence
247/// exists, because on Apple it is a hard limit and not a starting guess: there is
248/// no software fallback behind a VideoToolbox session that fails to create. `None`
249/// remains "unbounded" for callers with no decode cost at all (the benches' other
250/// ids, and every test above that is about the bitrate phases).
251///
252/// ### A cut must not fund an upgrade
253///
254/// Hiding tiles FREES bitrate, and the upgrade phase below will spend it on the
255/// survivors — a 32-tile gallery cut to 8 can afford the stage tile at `Source`
256/// where it could not before. That is correct when the cut was the platform's
257/// STATIC session cap (32 tiles on Apple's 16 says nothing about this box's CPU),
258/// and wrong when it was the dynamic controller cutting on evidenced audio-mix
259/// lateness: trading 24 thumbnails for one 720p decode is not obviously a saving,
260/// and it is certainly not what "the CPU is short" asked for.
261///
262/// This function does not know which of the two it is being handed, and deliberately
263/// stays pure rather than growing a mode flag: the caller expresses the difference
264/// where it is already expressed, in the DEMANDS. While its budget sits below the
265/// platform ceiling the shell folds [`cpu_crisis_cap`] into every tile's demand, so
266/// the ladder the upgrade phase can walk simply stops below the rungs whose decode
267/// the receiver has evidenced it cannot afford. See `call::policy::DecodeBudget`.
268///
269/// ## The upgrade order: cheapest marginal step first, priority as the tiebreak
270///
271/// Every tile's whole ladder is expanded into one flat list of single-rung steps,
272/// sorted by `(step price, tile priority)`, and the allocator takes the longest
273/// PREFIX of that list the budget can pay for.
274///
275/// Two properties are bought by that shape, and both are load-bearing:
276///
277/// * **Monotone in the budget.** The step sequence does not depend on `budget_bps`
278///   at all, so more money can only ever take a longer prefix — no tile can be
279///   *lowered* by a raise. That is what makes the AIMD controller below safe to point
280///   at this function (a probe upward can never churn a tile down and back up), and
281///   it is why the phase takes a prefix rather than skipping over steps it cannot
282///   afford: skipping is not monotone (a bigger budget lets an earlier tile take a
283///   big step and eat the slack a later one was living on).
284/// * **No dead band.** Ordering by priority instead — the obvious rule — halts the
285///   whole phase at the first *expensive* step, which for a screen share was once its
286///   only step: 200 kbps → 2.5 Mbps. Every budget in `[floor + ε, floor + 2.3 Mbps)`
287///   then spent nothing at all while every camera sat on a thumbnail, and the AIMD
288///   probing across that band was open-loop — measured as a permanent source⇄low
289///   resubscribe cycle on the shared QUIC connection against a ~3 Mbps link.
290///   Cheapest-first also maximises tiles improved per bit, which is the same thing a
291///   gallery view wants.
292///
293/// The residual cost: the screen's steps still land behind every camera's 290 kbps
294/// one — an upgrade-phase priority inversion, in a function whose other two phases
295/// put the screen first. Screen legibility is protected by the two phases that
296/// matter for it — the screen is guaranteed its `SCREEN_LOW_RUNG` floor (360p,
297/// legible, frame-rate-degraded) and is the LAST thing the deficit phase demotes —
298/// so what is lost is sharpness on a link that is already short, not readability.
299///
300/// `crate::SCREEN_MID_RUNG` is the other half of the answer, and it is now shipped:
301/// the share's ladder is `200 kbps → 1.1 Mbps → 2.5 Mbps`, so its cheapest step is
302/// 900 kbps rather than 2.3 Mbps and a mid-sized budget buys a sharp 720p30 share
303/// instead of stopping at the legibility floor. It cost the two things its absence
304/// used to buy — `layer`'s ranking carve-out is now an explicit guard rather than a
305/// consequence of cardinality, and the producer's screen low layer derives its
306/// geometry per rung (`camera_tx`'s pattern) rather than fixing it at open.
307///
308/// ### Why a step never sorts ahead of the step it depends on
309///
310/// A tile's own ladder order is guaranteed structurally, not by the data: each step
311/// sorts on the running MAXIMUM of its tile's deltas so far, which is non-decreasing
312/// along the ladder by construction, and the sort is stable, so equal keys keep
313/// insertion (ladder) order. Both shipped ladders happen to ascend already — asserted
314/// in debug builds below — but a future rung whose delta dipped would otherwise let
315/// the allocator hand a tile rung 3 without rung 2, which is not a rung at all.
316pub fn allocate_video(
317    tiles: &[TileRequest],
318    budget_bps: u64,
319    decode_budget: Option<usize>,
320) -> Vec<QualityRequest> {
321    // Hidden tiles pass through untouched and are excluded from every phase — they
322    // subscribe to nothing, decode nothing and cost nothing.
323    let mut out: Vec<QualityRequest> = tiles.iter().map(|t| t.demand).collect();
324    let mut order = served_order(tiles, None);
325
326    // ── Decode budget: a hard cap on how many tiles may own a decoder ──
327    // The cut is the TAIL of that same order, so what survives is exactly
328    // `served_order(tiles, decode_budget)` — which is what the caller prices its
329    // budget observation over. Pinned rather than argued.
330    if let Some(k) = decode_budget {
331        for &i in order.iter().skip(k) {
332            out[i] = hidden(tiles[i].source, tiles[i].demand);
333        }
334        order.truncate(k);
335    }
336    debug_assert_eq!(
337        order,
338        served_order(tiles, decode_budget),
339        "the decode cut and `served_order` disagree about who is served"
340    );
341
342    // ── Phase 1: the floor ──
343    let mut total: u64 = 0;
344    for &i in &order {
345        out[i] = floor(tiles[i].source, tiles[i].demand);
346        total += price(tiles[i].source, out[i]);
347    }
348
349    // ── Phase 2: the deficit ──
350    let mut demoted = false;
351    while total > budget_bps && order.len() > 1 {
352        let i = order.pop().expect("len > 1");
353        total -= price(tiles[i].source, out[i]);
354        out[i] = hidden(tiles[i].source, tiles[i].demand);
355        demoted = true;
356    }
357    // A receiver that could not afford everyone's floor has no business buying rungs.
358    if demoted {
359        return out;
360    }
361
362    // ── Phase 3: the upgrade ──
363    // Expand every tile's remaining ladder into one flat list of single-rung steps…
364    let mut steps: Vec<Step> = Vec::new();
365    for &i in &order {
366        let t = &tiles[i];
367        let (mut at, mut key) = (out[i], 0u64);
368        while let Some(next) = next_step(t.source, at, t.demand) {
369            let delta = price(t.source, next) - price(t.source, at);
370            debug_assert!(
371                delta >= key,
372                "{:?}'s ladder has a cheaper step ({delta}) above a dearer one ({key}) — the \
373                 running-max key below still orders it correctly, but `low_rungs` no longer \
374                 ascends in price and `debug_assert_ascending` should have caught it first",
375                t.source
376            );
377            // The running max, not `delta`: see the ladder-order note on this function.
378            key = key.max(delta);
379            steps.push(Step {
380                tile: i,
381                to: next,
382                cost: delta,
383                key,
384            });
385            at = next;
386        }
387    }
388    // …order it cheapest-first, priority breaking ties, and buy the longest prefix
389    // that fits. `sort_by_key` is stable, which is what keeps each tile's own steps in
390    // ladder order behind their (equal) keys.
391    steps.sort_by_key(|s| (s.key, priority(&tiles[s.tile])));
392    for s in &steps {
393        if total + s.cost > budget_bps {
394            break;
395        }
396        total += s.cost;
397        out[s.tile] = s.to;
398    }
399    out
400}

402/// One single-rung upgrade, as the upgrade phase queues it.
403struct Step {
404    /// Index into the caller's `tiles`/`out`.
405    tile: usize,
406    /// What this tile is allocated once the step is taken.
407    to: QualityRequest,
408    /// What taking it adds to the total.
409    cost: u64,
410    /// Sort key: `cost`, raised to the running maximum along this tile's ladder so a
411    /// step can never sort ahead of the step it depends on. See [`allocate_video`].
412    key: u64,
413}

415/// The total price of the SERVED tiles' own demands — the ceiling [`VideoBudget`]
416/// probes toward. It gates the PROBE and never truncates the estimate: climbing past
417/// what anyone actually wants would climb open-loop against no signal at all (exactly
418/// what `RateController::on_feedback_idle` exists to prevent on the send side), but a
419/// momentarily low ceiling — a grid scrolled entirely off screen, a peer who turned
420/// their camera off — says nothing about the link.
421///
422/// `decode_budget` must be the SAME value handed to [`allocate_video`] on this pass:
423/// a tile the decode cut hides subscribes to nothing, so counting its demand would
424/// have the controller probe toward bits nobody will ever ask for. See
425/// [`served_order`].
426pub fn demand_ceiling_bps(tiles: &[TileRequest], decode_budget: Option<usize>) -> u64 {
427    served_order(tiles, decode_budget)
428        .into_iter()
429        .map(|i| price(tiles[i].source, tiles[i].demand))
430        .fold(0u64, u64::saturating_add)
431}

433/// What it costs to give every SERVED tile its cheapest rung — the output of
434/// [`allocate_video`]'s floor phase, priced. The budget controller needs it for two
435/// unrelated jobs: it is the target the join-time seed reaches for
436/// ([`BudgetObservation::floor_bps`]), and it is the line the demote dwell measures
437/// "below" against ([`BudgetConfig::demote_dwell_us`]).
438///
439/// Same `decode_budget` contract as [`demand_ceiling_bps`], and here it is the more
440/// consequential of the two: the join seed raises a fresh budget outright to this
441/// figure, so floors belonging to tiles the decode cut has already hidden would hand
442/// the survivors a budget sized for a gallery that is not being rendered.
443pub fn floor_cost_bps(tiles: &[TileRequest], decode_budget: Option<usize>) -> u64 {
444    served_order(tiles, decode_budget)
445        .into_iter()
446        .map(|i| price(tiles[i].source, floor(tiles[i].source, tiles[i].demand)))
447        .fold(0u64, u64::saturating_add)
448}

452/// Starting total video budget: **4 Mbps**, which is the figure LiveKit publishes for
453/// a 25-person meeting and roughly double Zoom's quoted 2.0 Mbps for a 25-tile
454/// gallery. It is a *probe*, not a measurement — [`VideoBudget`] walks it up and down
455/// from here — but the starting point decides what a 32-peer join costs in its first
456/// second, which is the moment a call is most fragile.
457pub const VIDEO_BUDGET_START_BPS: u64 = 4_000_000;
458
459/// The budget floor: two thumbnail rungs, rounded up. Below this a receiver is not
460/// having a video call, and letting the AIMD walk further down would only feed the
461/// deficit phase tiles to blank.
462pub const MIN_VIDEO_BUDGET_BPS: u64 = 300_000;
463
464/// **8 Mbps**, ≈60 thumbnail rungs — the ceiling on the whole controller, and it wears
465/// two hats deliberately rather than being split into two numbers that would have to
466/// be kept in a fixed relation to each other:
467///
468/// * the **join seed** ([`BudgetObservation::floor_bps`]) may raise a fresh budget to
469///   whatever its tiles' floors cost, up to here. Without that, a 40-peer join spends
470///   its first pass at [`VIDEO_BUDGET_START_BPS`] — under the 5.2 Mbps those forty
471///   thumbnails cost — so the deficit phase hides ten tiles, and because a fresh
472///   `LayerHysteresis` has no history to debounce against, all ten blank immediately
473///   and ramp back one tick at a time. Seeding to the floor makes the receiver's first
474///   answer "everyone small", which is what the floor phase exists to say.
475/// * the **hard cap** on the probe. The budget is spent in PRICED rungs, and priced
476///   spend systematically overstates received bits (a `Capped` tile receives the
477///   producer's cross-receiver-minimum shared layer, which is usually cheaper than the
478///   cap it asked for), so a clean receiver can climb past what its link has ever
479///   evidenced. [`BudgetObservation::ceiling_bps`] does not stop that: it is a DEMAND
480///   ceiling, and 60 tiles asking for the source raise it to 90 Mbps. 8 Mbps is above
481///   any gallery a real receiver renders and below any link this could mislead.
482pub const VIDEO_BUDGET_START_CAP_BPS: u64 = 8_000_000;

484/// One subscribed video track's delivery evidence for this pass, read off the
485/// per-pipeline downlink state the reconcile loop already samples — always as a PAIR:
486/// what the track is managing to deliver, and what it was allocated.
487#[derive(Debug, Clone, Copy, PartialEq, Eq)]
488pub struct TrackDelivery {
489    pub source: VideoSource,
490    /// This track's own hysteretic delivery conclusion
491    /// ([`crate::downlink::DownlinkDemand::current`]): `Source` while frames are
492    /// arriving, a `Capped` bitrate once a full evaluation window has seen most of
493    /// them fail to.
494    pub delivered: QualityRequest,
495    /// The rung [`allocate_video`] granted this tile for the pass that produced
496    /// `delivered`.
497    pub allocated: QualityRequest,
498}

500/// DEFICIENT, in LiveKit's `StreamAllocator` sense: **any** subscribed track is
501/// failing to deliver what this receiver ASKED IT FOR. One starved track is enough —
502/// the budget is shared, so an overshoot shows up wherever the link happens to drop it
503/// first, not democratically across every track.
504///
505/// ## Why the comparison is against the allocation and not against the source
506///
507/// "This track has capped below its source rung" is the wrong predicate, and it fails
508/// in the direction that blanks a call. A track's cap is a per-track,
509/// per-*sender*-link fact: one remote peer on hotel wifi is capped for as long as they
510/// stay on it, and one uplink-constrained sender's frames never arrive for ANY
511/// receiver. Read as evidence about *this* receiver's downlink it is both sticky and
512/// undamped — the predicate stays true forever, the budget sheds 15% every sustain
513/// window, and a 32-tile gallery walks to the 300 kbps floor in about sixteen seconds
514/// with thirty of its tiles hidden, because of one peer nobody was watching closely.
515///
516/// The receiver-side question is narrower and answerable: *is this track delivering
517/// what the budget bought it?* A peer allocated the thumbnail rung and delivering the
518/// thumbnail rung is not evidence of anything, however far below its own source that
519/// is. Only a track delivering strictly LESS than its allocation says the receiver
520/// asked for more than it can take — which is exactly what the budget is a controller
521/// for.
522pub fn downlink_deficient(tracks: &[TrackDelivery]) -> bool {
523    tracks
524        .iter()
525        .any(|t| price(t.source, t.delivered) < price(t.source, t.allocated))
526}

528/// Tunables for [`VideoBudget`].
529#[derive(Debug, Clone, Copy)]
530pub struct BudgetConfig {
531    pub start_bps: u64,
532    pub min_bps: u64,
533    /// Additive increase per probe step — ONE thumbnail rung, i.e. the budget grows
534    /// by exactly the price of one more small tile each time it is found stable.
535    pub increase_bps: u64,
536    /// Minimum spacing between increase steps. The reconcile tick (500 ms), so a
537    /// recovering link regains one tile's worth of budget per pass.
538    pub increase_interval_us: i64,
539    /// Multiplicative decrease on a sustained deficit. **0.85** — the same backoff
540    /// WebRTC's loss controller applies at 30% loss (`1 − 0.5·loss`), and one step
541    /// sheds ~600 kbps at the starting budget: enough to clear a real overshoot in
542    /// two steps, small enough that a marginal one costs a single tile its rung.
543    pub decrease_factor: f64,
544    /// How long the deficit must persist before the first backoff, and the minimum
545    /// spacing between backoffs after it. One full
546    /// [`crate::downlink::DownlinkConfig::eval_interval_us`], so a single bad window
547    /// — a burst, a reorder, one dropped GOP — can never move the budget.
548    pub deficit_sustain_us: i64,
549    /// The hard ceiling on the estimate and the limit on the join seed — see
550    /// [`VIDEO_BUDGET_START_CAP_BPS`].
551    pub cap_bps: u64,
552    /// How long the budget must sit CONTINUOUSLY below the tiles' floor cost before
553    /// [`allocate_video`]'s deficit phase is allowed to start hiding tiles. Until then
554    /// [`VideoBudget::observe`] hands out the floor instead — a bounded, honestly
555    /// priced overshoot.
556    ///
557    /// **1.5 s**, deliberately the same figure as the client's
558    /// `call::policy::LAYER_SWITCH_DEBOUNCE`, and for the same reason: that constant
559    /// is how long a *layer* change must persist before it actuates, and hiding a tile
560    /// is a layer change. Without it, a link whose capacity sits near the floor cost
561    /// makes the AIMD sawtooth straddle that line, and the bottom few tiles blink at
562    /// roughly one cycle every 6–7 s for as long as the call lasts. The hysteresis
563    /// downstream cannot absorb it — the sawtooth is slower than its window.
564    pub demote_dwell_us: i64,
565    /// A gap between observations longer than this is treated as a restart rather than
566    /// as elapsed time. The reconcile loop only allocates while video is live, so a
567    /// paused call (or a backgrounded app) leaves `last_increase_us` arbitrarily stale
568    /// and the first pass after the resume would collect a probe step it did not
569    /// observe a link for. Four reconcile ticks.
570    pub observe_gap_reset_us: i64,
571}

589/// One reconcile pass, as [`VideoBudget::observe`] consumes it. Four numbers with two
590/// different vintages, which is worth being explicit about:
591///
592/// * `deficient` and `committed_bps` describe the allocation that was **in force**,
593///   i.e. the one this receiver committed to on the PREVIOUS pass. They cannot be
594///   otherwise: the budget has to be decided before the allocation it produces exists,
595///   so the evidence about an allocation is always one tick behind it. At a 500 ms
596///   tick against a 1 s sustain window that lag costs nothing.
597/// * `ceiling_bps` and `floor_bps` describe the tiles as they are RIGHT NOW, because
598///   they are properties of the roster and the layout rather than of the link.
599#[derive(Debug, Clone, Copy, Default)]
600pub struct BudgetObservation {
601    /// [`downlink_deficient`] over the tracks that had a live pipeline last pass.
602    pub deficient: bool,
603    /// What this receiver is actually committed to receiving right now: the priced sum
604    /// ([`request_bps`]) of the subscriptions the reconcile loop last applied, AFTER
605    /// `LayerHysteresis`.
606    ///
607    /// The controller refuses to cut while this exceeds the budget, and that is the
608    /// point of carrying it. The hysteresis can hold a committed `Source`
609    /// subscription for seconds after the allocator demoted it (1.5 s debounce, 6 s
610    /// dwell); across that window the receiver genuinely IS overspending, so it stays
611    /// deficient — and a controller that reacted would shed 15% per second for a cut
612    /// it had already made and was merely waiting on. Measured at 3.8 → 1.43 Mbps,
613    /// which then blanks cameras for a reason that has nothing to do with them.
614    pub committed_bps: u64,
615    /// [`demand_ceiling_bps`] — the total price of what the tiles are asking for. Gates
616    /// the probe.
617    pub ceiling_bps: u64,
618    /// [`floor_cost_bps`] — what every visible tile's cheapest rung costs together.
619    /// Seeds a fresh budget and anchors the demote dwell.
620    pub floor_bps: u64,
621}
622
623/// AIMD on the receiver's **total** video budget.
624///
625/// Purpose-built rather than a second [`crate::congestion::RateController`]: that one
626/// consumes a loss *fraction* and climbs multiplicatively toward a fixed ceiling,
627/// where this consumes a DEFICIENT/STABLE verdict, climbs additively (one tile at a
628/// time — a total budget shared by N tiles must not jump N tiles' worth in one step),
629/// and re-clamps to a ceiling that moves every pass with what the tiles are asking
630/// for. Reusing it would have meant synthesising a fake loss fraction and calling
631/// `set_max_bps` on every tick, which is a worse description of this than 40 lines.
632///
633/// Sans-IO: `now_us` is the only clock.
634#[derive(Debug)]
635pub struct VideoBudget {
636    cfg: BudgetConfig,
637    budget_bps: u64,
638    /// What the last [`Self::observe`] handed the allocator. Equal to `budget_bps`
639    /// except while the demote dwell is holding the floor above it.
640    allocation_bps: u64,
641    /// `None` until the first observation — a fresh controller must not immediately
642    /// probe above its start value on an arbitrary caller clock.
643    last_increase_us: Option<i64>,
644    /// The previous observation's clock, so a long gap can be told from elapsed time.
645    last_observe_us: Option<i64>,
646    /// When the current uninterrupted run of deficient passes began.
647    deficient_since: Option<i64>,
648    /// When the budget last dropped below the tiles' floor cost, cleared the moment it
649    /// covers the floor again — the demote dwell's clock.
650    below_floor_since: Option<i64>,
651    /// Whether ANY deficiency has been observed on this controller. Latched, and it
652    /// gates the join seed: a receiver with evidence about its link must not have that
653    /// evidence overwritten by a roster that got bigger.
654    saw_deficiency: bool,
655}
656
657impl VideoBudget {
658    pub fn new(cfg: BudgetConfig) -> Self {
659        let budget_bps = cfg
660            .start_bps
661            .clamp(cfg.min_bps, cfg.cap_bps.max(cfg.min_bps));
662        Self {
663            cfg,
664            budget_bps,
665            allocation_bps: budget_bps,
666            last_increase_us: None,
667            last_observe_us: None,
668            deficient_since: None,
669            below_floor_since: None,
670            saw_deficiency: false,
671        }
672    }
673
674    /// Fold one reconcile pass ([`BudgetObservation`]) and return the budget to
675    /// allocate against.
676    pub fn observe(&mut self, obs: BudgetObservation, now_us: i64) -> u64 {
677        // A gap far longer than a tick is not elapsed time this controller watched —
678        // the reconcile loop only allocates while video is live, so a pause of any
679        // length lands here as one enormous step. Restart every clock rather than
680        // paying out a probe step, a backoff, or a dwell expiry earned by an interval
681        // nothing was observed over.
682        let resumed = self
683            .last_observe_us
684            .is_some_and(|t| now_us - t > self.cfg.observe_gap_reset_us);
685        self.last_observe_us = Some(now_us);
686        if resumed {
687            self.last_increase_us = Some(now_us);
688            self.deficient_since = None;
689            self.below_floor_since = None;
690        }
691
692        let last = *self.last_increase_us.get_or_insert(now_us);
693        if obs.deficient {
694            self.saw_deficiency = true;
695            let since = *self.deficient_since.get_or_insert(now_us);
696            // Never cut while the overspend is still PENDING actuation: if the
697            // committed subscriptions cost more than the budget, the receiver is
698            // deficient because a cut the allocator already made has not reached the
699            // wire yet (`LayerHysteresis`). Freeze — the deficit clock keeps running,
700            // so the cut lands the moment the commitment catches up and the link is
701            // still short.
702            if now_us - since >= self.cfg.deficit_sustain_us && obs.committed_bps <= self.budget_bps
703            {
704                self.budget_bps = (self.budget_bps as f64 * self.cfg.decrease_factor) as u64;
705                // Re-arm both clocks: the next backoff is another sustain window
706                // away, and a backoff must not be undone by a probe on the next tick.
707                self.deficient_since = Some(now_us);
708                self.last_increase_us = Some(now_us);
709            }
710        } else {
711            // A single clean pass re-arms the window. That is the anti-oscillation
712            // contract: a link flapping in and out of deficit around a boundary never
713            // accumulates a full sustain window and so never backs off at all.
714            self.deficient_since = None;
715            // Probe only while somebody could use the extra. The ceiling is a gate on
716            // the CLIMB, not a clamp on the estimate — truncating to it would let a
717            // grid scrolled off screen (ceiling ≈ 0 for a pass or two) throw away a
718            // link estimate the receiver would then have to re-earn one rung per tick,
719            // right as the tiles come back.
720            if self.budget_bps < obs.ceiling_bps && now_us - last >= self.cfg.increase_interval_us {
721                self.budget_bps = self.budget_bps.saturating_add(self.cfg.increase_bps);
722                self.last_increase_us = Some(now_us);
723            }
724        }
725
726        // The join seed, until this controller has learned anything about its link:
727        // cover the tiles' floor outright rather than making a 40-peer join hide ten
728        // people and buy them back one per tick. Bounded by the cap — see
729        // [`VIDEO_BUDGET_START_CAP_BPS`] for both of its roles.
730        if !self.saw_deficiency {
731            self.budget_bps = self.budget_bps.max(obs.floor_bps.min(self.cfg.cap_bps));
732        }
733        self.budget_bps = self
734            .budget_bps
735            .clamp(self.cfg.min_bps, self.cfg.cap_bps.max(self.cfg.min_bps));
736
737        // The demote dwell: below the floor, keep handing out the floor until the
738        // shortfall has held for `demote_dwell_us`. The estimate itself is untouched
739        // (so a genuine collapse still walks down), and the overshoot is bounded by one
740        // floor cost and priced honestly — the alternative is the bottom tiles blinking
741        // once a sawtooth.
742        self.allocation_bps = if self.budget_bps < obs.floor_bps {
743            let since = *self.below_floor_since.get_or_insert(now_us);
744            if now_us - since < self.cfg.demote_dwell_us {
745                obs.floor_bps
746            } else {
747                self.budget_bps
748            }
749        } else {
750            self.below_floor_since = None;
751            self.budget_bps
752        };
753        self.allocation_bps
754    }
755
756    /// The link ESTIMATE — what the AIMD believes this receiver can take. Never
757    /// recomputed; a faithful projection of the last [`Self::observe`].
758    pub fn budget_bps(&self) -> u64 {
759        self.budget_bps
760    }
761
762    /// What the last [`Self::observe`] actually handed [`allocate_video`]. Differs from
763    /// [`Self::budget_bps`] only while the demote dwell is holding the floor above a
764    /// collapsed estimate.
765    pub fn allocation_bps(&self) -> u64 {
766        self.allocation_bps
767    }
768}

1387    /// The ladder is WALKED, never jumped: as the budget rises a tile visits every rung
1388    /// it owns, in order, and never appears on one without having appeared on the one
1389    /// below it. That is a strictly stronger statement than monotonicity (which only
1390    /// forbids going *down*) and it is what the upgrade phase's per-tile ordering
1391    /// guarantee buys: a tile handed rung 3 without rung 2 is subscribed to a layer
1392    /// nobody sized for it.
1393    ///
1394    /// The guarantee itself is structural, not data-dependent — each step sorts on the
1395    /// running maximum of its tile's deltas, so it survives a future rung whose step
1396    /// were cheaper than the one below it. No public type here can express such a
1397    /// ladder, so this sweeps the shipped ones and the `debug_assert` in the phase
1398    /// covers the rest.

1405            silent(4, QualityRequest::Source),
1406        ];
1407        // Rung index on this tile's own ladder; `Hidden` is below all of them.

1410                QualityRequest::Hidden(_) => -1,

1412                QualityRequest::Capped(bps) => low_rungs(t.source)
1413                    .iter()
1414                    .position(|g| rung_bps(t.source, *g) == bps)

1644    /// THE deficiency predicate, and the distinction the whole controller rests on:
1645    /// deficient means "short of what I ASKED FOR", never "short of the source".

1647    /// A remote peer on a bad uplink is capped below its own source for as long as they

1649    /// permanent, and a permanent deficiency is a permanent 15%-per-second backoff. The
1650    /// question that can actually be answered is whether the tile is getting the rung
1651    /// the budget bought it.

1658        assert!(!downlink_deficient(&[track(
1659            Capped(375_000),
1660            Capped(thumb())
1661        )]));
1662        assert!(!downlink_deficient(&[track(
1663            Capped(thumb()),
1664            Capped(thumb())
1665        )]));
1666        assert!(
1667            downlink_deficient(&[track(Capped(thumb() - 1), Capped(thumb()))]),
1668            "one bit under what it was given IS short"
1669        );
1670        // A tile allocated the source, and a link that cannot carry it.
1671        assert!(!downlink_deficient(&[track(Source, Source)]));
