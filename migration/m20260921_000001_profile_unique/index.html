Two membership-hygiene constraints the tables were missing.

profile(user_id, community_id) is unique. A community profile is a user’s identity in that community, not their membership of it, so leaving keeps the row — and a rejoin used to mint a second one, after which the merged read picked whichever the planner returned first. NULL community_id is the global profile, and both backends treat NULLs in a unique index as distinct, so the one global row per user is unaffected by this index (nothing here constrains it).

community_ban.banned_by and community_invite.created_by release instead of cascading. Both pointed at user with ON DELETE CASCADE, so deleting a moderator deleted the bans they had issued — the standing refusal vanished and everyone they had banned could walk back in. The actor is provenance, not ownership: the columns become nullable and the foreign keys ON DELETE SET NULL, so the ban outlives the account that wrote it and the row simply stops naming anyone.

Postgres can alter both in place. SQLite cannot alter a column’s nullability or a foreign key at all, so each table is rebuilt through the same sea-query builder that created it — which is what keeps the rebuilt column types identical to the originals by construction rather than by a hand-written CREATE TABLE that has to be kept in step.
