The text index over community_space_message.search_text — the one structure POST /search reads, in each backend’s own idiom.

Postgres gets a PGroonga index on the column itself. Nothing else changes: the index is maintained by the write that sets search_text, in that write’s own transaction, so a search is read-your-writes for free.

SQLite (tests, and local dev — the backend’s default database is sqlite::memory:) has no such thing, so it gets an external-content FTS5 table shadowing the column plus the three triggers that keep it in step. External content means the index stores only the terms; the rows stay in community_space_message and are reached by rowid. Same transaction, same guarantee.

§The rowid caveat

community_space_message has a UUID primary key, so its rowid is SQLite’s implicit one — and VACUUM may renumber implicit rowids, which would silently point every index entry at the wrong message. The backend never VACUUMs, and POST /internal/messages/reindex issues an FTS 'rebuild' after its walk, which is the repair if one ever happens.

Tokenizers differ deliberately: PGroonga’s default (TokenBigram + NormalizerAuto) segments CJK, unicode61 does not. Dev has no CJK segmentation; production does.
