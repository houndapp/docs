Sentry policy for the Rust client: what becomes an event, what stays a breadcrumb, and what every event carries.

TWO Sentry clients live in this process — Dart’s (SentryFlutter.init) and Rust’s (crate::api::init_sentry) — each with its own scope and breadcrumb ring, each attaching only to failures on its own side. This module is the Rust half’s policy. Its job is to make an event self-contained: a bare message with no story, no join key and no app state is not triageable, and every rule below was earned by an event that wasn’t.

§What becomes an event

  • Only first-party ERROR. A dependency’s error-level hygiene warning — iroh::socket’s “Endpoint dropped without calling Endpoint::close” — is not an app failure. Promoted, it files an issue with no stack, no user and nothing to act on; demoted, it still shows up in the breadcrumb trail of whatever first-party failure follows it. See is_first_party.
  • INFO and above become breadcrumbs. The core’s info! lines are the narrative (“session restore: …”, “call joined”); without them an event says what broke and never how it got there.
  • One event per callsite per EVENT_COOLDOWN. A first-party error! on a hot path (a per-frame encode failure) would otherwise file thousands of identical issues and burn the project quota. Repeats demote to breadcrumbs, so the burst stays visible locally.

§What every event carries

enrich stamps the join key (LAUNCH_ID_TAG — the only thing tying a Rust event to the Dart event from the same launch, since the two clients share no trace), what this process is (APP_ROLE_ENV), how long it had been up, whether a call was live, and the audio pipeline’s verdict when one was.

Structs§

AppSnapshot
What the live client can say about itself at event time. None before the client exists — the reporter comes up first, deliberately, so a startup crash still reports.
AudioSnapshot
The audio pipeline’s self-assessment, in both forms (see hound_client::audio_report::Diagnosis): a low-cardinality stage token fit for a tag, and the paste-able report behind it.
VideoSnapshot
The video pipeline’s self-assessment, in the same two forms as AudioSnapshot (see hound_client::video_report::Diagnosis).

Constants§

APP_ROLE_ENV
Env var naming what this process is: user (the default) or a runner label set by whatever launched it — today ci-smoke, from the nightly launch-smoke job in .github/workflows/nightly.yaml. A real install never sets it. Without it a runner’s failures land in the same issue stream as users’ and inflate every impact count, which is how you end up triaging a robot.
EVENT_COOLDOWN 🔒
Minimum spacing between Sentry events from one tracing callsite.
LAUNCH_ID_TAG
Tag joining a Rust event to the Dart event from the same process launch. The two SDKs mint independent trace ids, so without this there is no query that returns both halves of one incident; the Dart side reads it back over the bridge (see api::sentry_launch_id) and tags its own client with the same value.

Functions§

admit 🔒
The rate limiter itself, over any key — split out from cooled_down so it is testable without synthesising tracing callsites.
app_role
See APP_ROLE_ENV. Read once — the environment does not change under us.
cooled_down 🔒
Whether this callsite may file an event again yet, recording the attempt if so.
enrich
Stamp an outgoing event with everything triage needs that the message itself can’t carry. Runs as the client’s before_send, i.e. after the scope and the default integrations have had their turn.
event_filter
The event-vs-breadcrumb decision for one tracing event. See the module docs for the three rules; DEBUG/TRACE are dropped entirely (they still reach the Dart log sink, which has its own filter).
is_first_party 🔒
Whether a tracing target is ours. Targets are module paths, so this is a prefix test; NB this crate’s target is its LIB name (rust_lib_houndchat), not the package name hound-frb.
launch_id
This launch’s id, minted on first use. Stable for the process lifetime.
uptime
How long this process has been reporting. Anchored on the first call, which crate::api::init_sentry makes at startup — milliseconds into the process, and the earliest point at which anything is reportable anyway.
uptime_bucket 🔒
Coarse uptime band, for filtering. The same message means different things at different ages — “endpoint dropped” seconds after launch or at teardown is lifecycle noise, the same line an hour in is the wedge — and the exact seconds (carried as uptime_seconds) are too high-cardinality to group by.
