Crash reporting: Rust panics → Sentry. Policy (event-vs-breadcrumb rules, event enrichment) lives in crate::telemetry; this is the bridge half.

Statics§

SENTRY_GUARD 🔒
The [sentry::ClientInitGuard] returned by [sentry::init], parked here for the process lifetime. Dropping it would flush and shut the client down, so it must outlive every later panic; a plain local would drop at the end of init_sentry.

Functions§

app_snapshot 🔒
The live client’s view of itself, for stamping onto an outgoing event. None before init_app — the reporter comes up first, deliberately, so a crash during startup still reports.
init_sentry
Install Sentry crash reporting. Idempotent — a second call is a no-op, so the UI can call this unconditionally on every (re)start without double-initialising.
sentry_app_role
What this process is — user, or the runner label its launcher set (see telemetry::APP_ROLE_ENV). Mirrored onto the Dart client so a nightly smoke run’s failures don’t inflate user-facing impact counts on either side.
sentry_launch_id
This launch’s Sentry join key, for the Dart client to tag its own events with.
sentry_set_user
Set (or, with id: None, clear) the Sentry-scoped user id for this process’s Rust-side client — ID only, no username/email (PII). Mirrors the Dart-side Sentry.configureScope call (see bootstrap.dart’s auth-state listener); the two are separate Sentry clients (Dart events vs. Rust panic events), so both need setting. A no-op when Sentry was never initialised (sentry-core’s scope calls no-op with no bound client).
