The persistent log file: where it lives, and how one instance’s file is rotated aside for the next.

The Dart log sink (crate::api::init_log) only exists while the app does — a user who reports “video froze last night” has nothing to attach. So every line the subscriber formats also lands in a file under the OS’s own log directory, which is where a support request can ask for it by name.

Rotation is per-INSTANCE, not per-size or per-day. A call session is the unit anyone debugs, and it maps to a process launch: one file per launch means “the run where it broke” is one file, not a slice of a rolling one. So startup renames the previous instance’s houndchat.log aside with ITS OWN end-of-run timestamp (the file’s mtime — naming it after this launch would label the log with a time nothing in it happened at), then keeps the newest KEEP renamed files. Five files total is enough history for “it also did this yesterday” without an unbounded directory.

Every step is best-effort. File logging is a diagnostic, and a diagnostic that can fail the launch it exists to explain is worse than no diagnostic: an unwritable directory, a rename the OS refuses, an undeletable stale file — each degrades to “no file this session” (or “one extra old file”) and is reported as a warn! once there is a subscriber to receive it, never as an error the caller has to handle.

Constants§

APP 🔒
The identifier every per-user hound directory is named for: the Flutter binary / pubspec name. Deliberately NOT the macOS bundle id (chat.hound.houndctl) nor the keyring service (chat.hound.app) — those are platform-registry keys; this is the human-facing directory a user is asked to open, and it is spelled the same on all three platforms.
CURRENT 🔒
This instance’s log file, inside log_dir. A fixed name, so a bug report can name one path on every platform.
KEEP 🔒
How many previous instances survive a rotation. Four renamed + the current file = the five persisted logs the app promises.
LOG_EXT 🔒
Extension shared by the current and the rotated files.
ROTATED_PREFIX 🔒
Prefix of a rotated (previous-instance) file. The stamp that follows is fixed-width UTC, so a lexicographic sort is an age sort — which is the whole of prune’s ordering logic.

is_rotated 🔒
Whether a path is one of OUR rotated files. Deliberately narrow: this function authorises deletions, so anything else the user left in the directory — including CURRENT, which has no stamp and so fails the prefix test — is not ours to remove.
log_dir 🔒
The OS’s idiomatic per-user log directory for this app, or None where the platform gives us no home to derive one from (a service account with no $HOME, a sandbox that denies it).
path
The current log file’s path, once init has run — None if it never did, or if the file could not be opened. Backs api::log_file_path/api::open_log_file.
prune 🔒
Delete all but the newest keep rotated files. Deletions are individually best-effort — one file the OS won’t unlink (open in a viewer on Windows) must not strand the rest.
rotate 🔒
Rename the previous instance’s file aside and drop everything past KEEP. now is only the fallback stamp for a file whose mtime is unreadable.
rotated_name 🔒
The rotated name for a file that last ran at at. UTC and fixed-width, to match the fmt layer’s own timestamps inside the file and to keep name order equal to age order (local time is neither — a DST fall-back reorders an hour).
