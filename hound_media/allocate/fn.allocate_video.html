pub fn allocate_video(
    tiles: &[TileRequest],
    budget_bps: u64,
    decode_budget: Option<usize>,
) -> Vec<VideoAllocation>
Expand description

Hand every visible tile the richest rung the total budget_bps can pay for, in priority order. Returns one QualityRequest per input, in input order.

Three phases, all in rung space:

  1. Floor — every visible tile is guaranteed its cheapest rung. A call does not silently drop people because the link is tight; it makes everyone small.
  2. Deficit — if even the floor overruns the budget, tiles are demoted to Hidden from the BOTTOM of the priority order until it fits (never the top-priority tile: a receiver that can afford nothing still watches one thing). That is a layer-AXIS move, so the caller’s existing layer-switch debounce (call::policy::LayerHysteresis) absorbs a transient dip rather than letting it blank tiles.
  3. Upgrade — the remaining budget buys single-rung steps, CHEAPEST FIRST.

decode_budget caps the number of tiles that may hold a decoder at all, independent of bitrate — a receiver can be CPU-bound long before it is bandwidth-bound. Applied first, since it decides the tile SET the other two phases work over.

The shipped client always passes a number: call::policy::DecodeBudget starts it at the platform’s static decode-session ceiling (hound_engine::api::Engine::decode_session_budget — 16 on every HW decoder, a thread-count prior on the software one) and halves it against RT audio-mix lateness, so a receiver sheds decoders to keep the audio thread scheduled. The ceiling reaches this function on the very first pass, before any evidence exists, because on Apple it is a hard limit and not a starting guess: there is no software fallback behind a VideoToolbox session that fails to create. None remains “unbounded” for callers with no decode cost at all (the benches’ other ids, and every test above that is about the bitrate phases).

§A cut must not fund an upgrade

Hiding tiles FREES bitrate, and the upgrade phase below will spend it on the survivors — a 32-tile gallery cut to 8 can afford the stage tile at Source where it could not before. That is correct when the cut was the platform’s STATIC session cap (32 tiles on Apple’s 16 says nothing about this box’s CPU), and wrong when it was the dynamic controller cutting on evidenced audio-mix lateness: trading 24 thumbnails for one 720p decode is not obviously a saving, and it is certainly not what “the CPU is short” asked for.

This function does not know which of the two it is being handed, and deliberately stays pure rather than growing a mode flag: the caller expresses the difference where it is already expressed, in the DEMANDS. While its budget sits below the platform ceiling the shell folds cpu_crisis_cap into every tile’s demand, so the ladder the upgrade phase can walk simply stops below the rungs whose decode the receiver has evidenced it cannot afford. See call::policy::DecodeBudget.

§The upgrade order: cheapest marginal step first, priority as the tiebreak

Every tile’s whole ladder is expanded into one flat list of single-rung steps, sorted by (step price, tile priority), and the allocator takes the longest PREFIX of that list the budget can pay for.

Two properties are bought by that shape, and both are load-bearing:

  • Monotone in the budget. The step sequence does not depend on budget_bps at all, so more money can only ever take a longer prefix — no tile can be lowered by a raise. That is what makes the AIMD controller below safe to point at this function (a probe upward can never churn a tile down and back up), and it is why the phase takes a prefix rather than skipping over steps it cannot afford: skipping is not monotone (a bigger budget lets an earlier tile take a big step and eat the slack a later one was living on).
  • No dead band. Ordering by priority instead — the obvious rule — halts the whole phase at the first expensive step, which for a screen share was once its only step: 200 kbps → 2.5 Mbps. Every budget in [floor + ε, floor + 2.3 Mbps) then spent nothing at all while every camera sat on a thumbnail, and the AIMD probing across that band was open-loop — measured as a permanent source⇄low resubscribe cycle on the shared QUIC connection against a ~3 Mbps link. Cheapest-first also maximises tiles improved per bit, which is the same thing a gallery view wants.

The residual cost: the screen’s steps still land behind every camera’s 290 kbps one — an upgrade-phase priority inversion, in a function whose other two phases put the screen first. Screen legibility is protected by the two phases that matter for it — the screen is guaranteed its SCREEN_LOW_RUNG floor (360p, legible, frame-rate-degraded) and is the LAST thing the deficit phase demotes — so what is lost is sharpness on a link that is already short, not readability.

crate::SCREEN_MID_RUNG is the other half of the answer, and it is now shipped: the share’s ladder is 200 kbps → 1.1 Mbps → 2.5 Mbps, so its cheapest step is 900 kbps rather than 2.3 Mbps and a mid-sized budget buys a sharp 720p30 share instead of stopping at the legibility floor. It cost the two things its absence used to buy — layer’s ranking carve-out is now an explicit guard rather than a consequence of cardinality, and the producer’s screen low layer derives its geometry per rung (camera_tx’s pattern) rather than fixing it at open.

§Why a step never sorts ahead of the step it depends on

A tile’s own ladder order is guaranteed structurally, not by the data: each step sorts on the running MAXIMUM of its tile’s deltas so far, which is non-decreasing along the ladder by construction, and the sort is stable, so equal keys keep insertion (ladder) order. Both shipped ladders happen to ascend already — asserted in debug builds below — but a future rung whose delta dipped would otherwise let the allocator hand a tile rung 3 without rung 2, which is not a rung at all.
