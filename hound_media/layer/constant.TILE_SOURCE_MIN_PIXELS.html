A visible tile larger than this — in physical pixels — takes the source rather than any below-source rung: it is past what the richest rung a tile’s SIZE may select (LOW_RUNG, and SCREEN_LOW_RUNG at the same geometry) can fill within TILE_UPSCALE_TOLERANCE_NUM/TILE_UPSCALE_TOLERANCE_DEN.

One boundary for both ladders, and it stayed one when SCREEN_MID_RUNG landed: that rung is reachable from the allocator, never from a tile’s size, so the screen ladder’s size boundary is still its floor rung’s coverage — the same 345 600 px, since the two floors share the 360p geometry. See tile_quality_request for why the size walk must stop there.

Worked examples, in the PHYSICAL pixels the UI actually reports (its own 16 px bucketing already applied, so these are the exact numbers that arrive), for the two shapes the shipped UI produces — tile_grid.dart’s maxCrossAxisExtent: 360 logical grid cell and its 96 px-tall filmstrip:

grid cell368×208 = 76 544 px → thumb720×400 = 288 000 px → low
filmstrip stamp176×96 = 16 896 px → thumb336×192 = 64 512 px → thumb
expanded / stage1280×720 = 921 600 px → sourcesource

The 2× grid cell is the case this boundary exists for: it is a genuine 720-wide surface, and filling it from a 320-wide thumbnail would be a 2.25× linear upscale of a face.
