pub fn plan_layers(requests: &[QualityRequest], source_bps: u64) -> LayerPlan
Expand description

Aggregate every receiver’s QualityRequest into the sender’s LayerPlan.

The whole demand-driven, coalesced, source-droppable policy in one pure function:

  • a receiver wanting Source (or a cap ≥ source — it can only ask for lower) keeps the source alive;
  • receivers wanting less than source collapse to ONE shared low layer at the minimum of their caps, so the weakest can still decode it (bounded to two total streams — no per-receiver explosion);
  • a QualityRequest::Hidden receiver keeps the low layer alive but is excluded from that minimum while anyone is actually rendering. A tile nobody is looking at must not decide the geometry everyone else watches;

§The accepted cost: a fully-hidden receiver set still pins the layer

min_cap.or(min_hidden) means a producer whose every receiver is hidden keeps encoding and publishing a thumbnail rung nobody is subscribed to — since off-screen tiles unsubscribe outright, that is a real, if small (~130 kbps plus one downscale+encode), waste. It is deliberate, and it buys the thing the off-screen policy is sold on: the _l0 decl stays in the roster, so a tile scrolling back into view is a subscribe on an already-live layer rather than a wait on a producer spinning an encoder up (the receiver-side equivalent of Octo’s “forward every layer so a switch is instant”). Tearing the layer down at zero visible receivers would trade an unhide’s latency for that 130 kbps, and the latency is what users feel.

crate::allocate has since landed, and it resolves the half of this that was always the receiver’s: a receiver now knows what its whole tile set costs, so an off-screen tile is a priced decision (Hidden costs zero against the budget, and the budget it frees is spent on the tiles that are on screen) rather than a guess. What it does NOT resolve is the producer half above — this fold is still what a sender does with a fully-hidden receiver set, and a producer cannot see any receiver’s budget. The ~130 kbps of pinned layer stays exactly as it is.

  • if NO receiver can take the source, send_source is false and only the low layer is published — the optimisation that stops encoding a stream nobody wants.

§The cap is a cross-receiver MINIMUM

Among receivers that are rendering, this is still one shared layer sized to the most-constrained of them: a peer showing a 180p thumbnail and a peer showing a 360p tile both get 180p. That is inherent to publishing one low layer rather than one per receiver, and excluding hidden tiles (above) only removes the pathological case.

crate::allocate resolves the half of this that was mis-stated as a producer problem. “Each track independently picking a rung” is gone: a receiver now ranks its whole tile set and hands out rungs against one total bitrate (and decode) budget, so it can no longer ask for more, in aggregate, than it can take — which is what actually collapsed a large call.

The coalescing itself is unchanged and remains. This fold is still a cross-receiver minimum, so a receiver whose allocator bought it the 360p rung still watches 180p if any other rendering receiver is on the thumbnail — and a receiver pinned to a rung it did not want still costs its producer that encode. Fixing that means publishing more than one low layer (per-receiver rungs, or a third simulcast track), which is a producer-side cost decision this function is deliberately not making. The allocator bounds what any one receiver asks for; it does not, and cannot, decide what a sender publishes.

With no receivers the source stays on (idle default; nothing to optimise yet). Pure/sans-IO → unit-tested below.
