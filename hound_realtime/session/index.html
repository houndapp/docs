Module session

Client-side session state, derived purely from transport lifecycle and ServerMessages.

ClientSession is a deterministic reducer. It holds no I/O: the shell tells it the transport came up or went down and hands it inbound frames; it answers with Actions to send and Events for the app.

§Why it owns subscriptions

Space subscriptions are connection state on the server — a reconnect lands on a fresh connection with no space rooms at all. So the reducer keeps two sets: what the app wants (desired, which outlives any connection) and what has been issued on the current one. Every ServerMessage::Welcome — the first one and every reconnect’s — reconciles them by re-issuing the whole desired set. A subscription therefore cannot be silently lost by a reconnect, which is the failure mode of tracking subscriptions at the transport.

Clearing issued on disconnect is what makes the reconciliation correct rather than optimistic.

§Subscriptions resync; message history does not

Re-issuing a subscription only restores the flow of events. Everything the server fanned out while this session had no connection was fanned out to a room it was not in, and no protocol frame replays it — so a client that only re-subscribes is silently missing whatever happened during the gap. That repair is a history re-fetch, which is the shell’s job (it owns the REST client), and all this reducer owes it is the one fact it cannot derive: whether a given ServerMessage::Welcome is the FIRST of this session or a reconnect’s. Event::Connected::reconnect carries it.

§Issued is not confirmed

A third set, confirmed, holds the spaces the server has said it joined (ServerMessage::Subscribed). issued only means “we wrote the frame”: between that and the server’s room join sit a task hop, a network, and the backend’s authorization lookups, and a message posted in that window reaches nobody. Only confirmed licenses a caller to believe it is receiving a space, which is what ClientSession::is_subscribed answers. A server too old to confirm (ServerMessage::Welcome::confirms_subscriptions absent) leaves the set empty forever — see ClientSession::confirms_subscriptions, which is how the shell knows not to wait.
