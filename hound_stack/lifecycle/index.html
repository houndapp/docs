The shared stack lifecycle: ensure the stack is up (reusing a live one), and — only when asked — tear it down again.

§Bring-up order

  1. docker compose up -d postgres mailpit iroh-relay, then postgres’s health check and mailpit’s.
  2. The host BACKEND, detached, on :8080.
  3. The host SFU, detached, once the backend answers — it registers itself with the backend, which is what makes voice routable.
  4. The host AUTH page, detached, on :3100 — last, because nothing waits on it and it needs nothing but a fixed backend URL.

The SFU is a HOST process, not the hound-sfu compose container (which compose.dev.yaml still defines for the prod-like topology). A container SFU advertises the Docker bridge address, so media leaves loopback — on macOS that is Local Network traffic behind a per-application privacy grant, silently dropped without one. On the host it binds AND advertises 127.0.0.1 (crate::sfu), so the only address a client is ever handed is loopback.

The auth page is a host process too (crate::auth), for build cost alone: its container was a release cargo build inside docker on every --fresh. So the dev stack builds NO docker image from this repo — the compose side is two pulls (postgres, mailpit) and the relay, whose image only cargo installs iroh-relay from crates.io.

§The contract

The stack is PERSISTENT. e2e, visual and up all “ensure up and keep”: a live stack is reused as-is, a missing one is brought up and left running when the command exits. Nothing tears down implicitly — no Drop, no end-of-run cleanup — because the expensive part of these flows is bring-up, and paying it once per working session instead of once per run is the entire point. The explicit paths are --teardown (what CI wants: run, then leave the host clean), hound-stack down, and --fresh (tear down first, then bring up from scratch).

“Live” is four typed checks, never a port probe (repair::probe): the backend answers GET /instance, the host SFU answers GET /health, the backend’s GET /internal/sfu/nodes reports a live non-draining node, AND the auth page answers GET /. A stack missing any of them would fail scenarios in a way that looks like a product bug, so it is never silently handed to the suite. Only a missing BACKEND means a full bring-up; with the backend answering, the rest is repaired in place (repair::plan): a silent SFU is spawned, a healthy-but-unregistered one restarted (it registers at startup), a silent auth page spawned. (The health check is also what stops a leftover CONTAINER SFU, registered but unreachable on loopback, from passing as live.)

§What still cleans up

A FAILED bring-up must not leave processes nobody knows about: whatever this invocation spawned is killed and its state entry removed. Compose is deliberately left as it is — a half-up compose stack holds no host resource the next attempt wants, and up -d is idempotent, so the next bring-up simply completes it. --fresh is the escape hatch when it is genuinely wedged.

§Staleness

Reuse always rebuilds the three binaries first (a no-op when nothing changed) and compares each built binary’s (mtime, len) against what the state file recorded for the running process. Different ⇒ that process is the old code: stop it and spawn the new one.

A restarted BACKEND also forces an SFU restart. The SFU’s registration is a 30 s heartbeat (REGISTER_INTERVAL in services/sfu/src/main.rs; the 5 s retry only applies to a FAILED post), while a backend restart empties the in-memory registry — so the registry can stay empty for up to 30 s, well past the wait a reuse is willing to do. Restarting the SFU re-registers it immediately. The auth page has no such coupling (stateless, fixed upstream URL): only its own rebuilt binary restarts it.

Noise contract: one console line per lifecycle step; every subprocess’s full output goes to its own artifact file (build.log, compose.log, backend.log, sfu.log, auth.log); a failure prints the relevant log’s tail inline. Success prints no log content at all.

Modules§

repair 🔒
What to do with whatever answers on the stack’s ports: the pure half of [super::is_live]’s successor. Probing is I/O (probe); turning the four probe results into a Plan is not (plan), so that is where the decision lives and what the tests cover.

Structs§

LiveStack
A stack this invocation has confirmed up — reused or just brought up. Holding one is NOT ownership: dropping it leaves the stack running.
StackBins
The three host binaries a stack runs, prebuilt (see build_stack_bins). Their (mtime, len) is also what the staleness check reads.
StackPaths
The stack’s fixed filesystem layout, relative to the repo root.

Constants§

COMPOSE_SERVICES 🔒
The compose services this stack starts. hound-sfu and hound-auth are deliberately NOT among them — both run on the host (see the module doc).

Functions§

backend_answers
Any HTTP response proves the server is up — an auth-gated 401 counts (the same rule as wait::wait_http_reachable).
build_stack_bins
Build the host backend, SFU and auth page in ONE cargo invocation, and give each this machine’s stable code signature if one is configured.
stop_recorded 🔒
Stop every recorded process: auth, then SFU, then backend. SFU before backend because it deregisters by exiting, and stopping it while the backend still answers keeps the registry honest for anything else watching.
teardown
Stop the recorded host processes (if any) and take the compose stack down.
