hound_stack::process

Module state 

Source
Expand description

The detached processes’ state file: target/hound-stack/stack.json.

The host backend, SFU and auth page all outlive the hound-stack invocation that started them (reuse-by-default — see crate::lifecycle), so the next invocation has to learn about them from disk rather than from Children it owns. This is that record, one entry per process: who to signal (pid), where its output went (log), and which binary it is running (binary + BinaryStamp) so a later run can tell “the same process is still fine” from “the binary on disk has moved on”.

One file for all of them, because they are one stack: a teardown stops whatever it finds, and a split record would strand a process.

Deliberately under <root>/target/, not CARGO_TARGET_DIR: the record describes processes running on THIS host against THIS checkout, and target/ is the one directory that is already both per-checkout and gitignored. It is not a build artifact and nothing consumes it but this crate.

Structs§

BinaryStamp
Identity of the built binary a running process was spawned from. Content hashing would be exact but costs a full read of a ~200 MB debug binary on every invocation; (mtime, len) moves whenever cargo relinks, which is the only way the binary can change here.
ProcessRecord
What one hound-stack invocation needs to know about a process some EARLIER invocation left running.
StackState
The stack’s detached processes, as last recorded. A missing entry means “hound-stack is not running one” — either nothing started it, or whatever answers on its port belongs to somebody else and must be left alone.
