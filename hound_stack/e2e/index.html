hound-stack e2e: ensure the stack is up, run the hound-testkit scenario suite (cargo nextest run -p hound-testkit --profile e2e) against it, collect artifacts. Mirrors the retired tools/houndbot/e2e.sh. Extra CLI args forward to cargo nextest run (e.g. an -E filter for a fast local iteration loop against one scenario file).

The stack is REUSED when one is already live and LEFT RUNNING afterwards (see crate::lifecycle for the contract). --fresh wipes and rebuilds it first — the landing gate’s shape, and the answer to any scenario that needs a pristine database; --teardown takes it down after the run, which is what CI wants.

The test binaries are compiled in a separate quiet pass (cargo nextest run --no-run, output → build.log) before the real run, so nextest.log holds test results, not compiler chatter.

§Remote-target mode (--target <url> / E2E_TARGET_URL)

Points the SAME suite at a DEPLOYED hound (staging, or a new cluster before DNS cuts over) instead of the local stack: no compose/backend bring-up, no teardown, no compose artifacts, and no local hound-sfu build. Never the default — the plain mise run e2e:call path is byte-for-byte what it always was.

Two things the operator owns in this mode:

  • Mail. Scenarios authenticate by magic link, read out of Mailpit — there is no other auth path here, and none is added. So the target backend must deliver its mail somewhere this process can read as MAILPIT_URL; for a cluster that means port-forwarding its Mailpit (kubectl port-forward -n hound svc/mailpit 8025:8025, then MAILPIT_URL=http://localhost:8025). A deployment wired to a real SMTP provider can’t run these scenarios at all.
  • DNS. E2E_RESOLVE=host:port:ip[,…] (curl --resolve shape) pins hostnames for the run, so a pre-cutover cluster is reachable at its real hostnames — TLS SNI/certs still validate. It reaches every reqwest client (auth + REST + Mailpit), NOT the realtime/media planes; see hound_testkit::remote for why, and for the /etc/hosts alternative that does cover them.
