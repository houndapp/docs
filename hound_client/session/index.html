Module session

Expand description

Auth/session lifecycle: where tokens live, how they persist, and how they refresh.

The crate must NOT depend on any platform keyring, so persistence is injected via the SessionStore trait — the host (Flutter via FRB) supplies a keyring-backed impl; tests use MemorySessionStore. Session owns the live tokens, tracks an AuthState snapshot for the reducer, and republishes the access token onto the shared RestClient so every request reads the current value.

The access token is short-lived (45 min), so it is rotated from three directions, all funnelled through ONE refresh_gate mutex — the single-flight guarantee, so a burst of simultaneous expiries costs exactly one exchange:

  • Proactive — a 30 s-tick background task refreshes once the token passes its half-life (refresh_due). Started by every path that installs a live session, aborted on sign-out.
  • On demand — RestClient calls Session::reauth_for through the Reauth hook installed here when a request comes back 401 expiredtoken, then retries it once. This is the net under a suspended laptop / a missed tick.
  • App resume — Session::ensure_fresh (the facade’s HoundClient::ensure_session_fresh), for a wake-up where neither of the above has run yet.

A refresh whose refresh token is rejected is unrecoverable: the session is signed out. Anything else (offline, a 5xx) is left alone — the next tick or request retries.

Constants§

REFRESH_FALLBACK_LEAD 🔒
The window before exp in which a refresh is due for a token we can’t compute a half-life for (no readable iat). Wide enough to survive a missed tick or two.
REFRESH_TICK 🔒
How often the proactive task re-checks whether the access token is past its half-life. Deliberately far shorter than the 45 min lifetime it guards: the check is a WALL-CLOCK comparison, so a short tick self-corrects across a laptop suspend (a single long timer armed for the half-life either fires hours late or, on some platforms, not at all — and the token is dead by then).
