The single, typed error surface for the whole client. Every command returns Result<T, HoundError>; the FRB layer maps this 1:1 onto a Dart sealed class so the UI matches on variants instead of parsing strings. Keep variants coarse + stable — they are a public contract the UI switches on.

§The error-code registry

Every error also carries a stable machine code: a category prefix plus a 3-digit number (AUTH003, MEDIA011, …). The Http variant is the one exception — its code is derived from the status (HTTP404) and never stored. Codes are what Sentry fingerprints on and what a support log greps for, so they outlive both build-shifted stack frames and the human message text.

Constructing errors. The typed constructors on HoundError (network, auth, …) are the ONLY sanctioned way to build a non-Http variant; Http comes from from_status or is built inline with its status. The struct variants exist for pattern matching, not for hand-assembly.

Registry rules.

  • Codes are append-only, and declaration order is the numbering: ALL[i]’s number is i + 1. Add at the end of a category’s list; never reorder, never renumber, never reuse a retired number, never repurpose one for a different failure. A code that stops being emitted stays in the enum (historical logs and Sentry issues still reference it). Inserting in the middle silently renumbers everything after it, so [tests::codes_are_numbered_by_declaration_order] fails the build on it — load-bearing, because the mirrored Dart enum renders the code string from the variant’s index rather than carrying the string across the bridge.
  • One code per distinct failure cause, not per call site. Several sites that fail the same way share a code; a site that can fail two different ways gets two.
  • Dynamic detail goes in the message only. Ids, URLs, counts, and wrapped upstream error text belong in the message so the code stays a fixed-cardinality label.
  • Every enum variant carries a doc comment naming its cause. That comment is the registry entry.
