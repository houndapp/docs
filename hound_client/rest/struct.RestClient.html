pub struct RestClient {
    http: OnceLock<Client>,
    base: Url,
    token: ArcSwapOption<String>,
    reauth: ArcSwapOption<Box<dyn Reauth>>,
}
Expand description

HTTP client bound to one backend base URL, carrying the optional session token. Cheap to clone-share via Arc<RestClient>; the token cell is interior-mutable.

Fields§

§http: OnceLock<Client>

Built on first request, not at construction: reqwest::Client::new runs macOS system-proxy discovery (SCDynamicStore), which stalls ~2 s in unbundled binaries (dev runs, every per-test process). Deferring it keeps constructors instant and moves the one-time cost onto the first actual HTTP call, off the caller’s startup path.

§base: Url§token: ArcSwapOption<String>

Current bearer token (None when signed out). Swapped atomically by auth.

§reauth: ArcSwapOption<Box<dyn Reauth>>

The installed refresh hook, if any. None (a client built without a Session) simply never retries an expired 401. Boxed because arc-swap’s RefCnt covers only Arc<T: Sized>, so the trait object needs the extra indirection to live in the cell.

async fn send( &self, endpoint: &str, build: impl Fn() -> RequestBuilder, ) -> Result<Response>

The request core every verb helper funnels through: attach the current bearer token, send, and — on a 401 expiredtoken with a Reauth hook installed — rotate the session and resend ONCE. At most one retry per call, so a backend that answers expiredtoken to a freshly minted token cannot loop us.

build is a closure, not a RequestBuilder, for two reasons: a builder is single-use (consumed by send), and re-invoking it re-reads the token cell, which is what makes the retry carry the rotated token rather than the dead one. It must therefore be a pure re-build — no side effects.

Source

fn refresh_failure( err: HoundError, endpoint: &str, rejection: &str, ) -> HoundError

What the caller is told when the refresh triggered by an expired 401 did not itself succeed.

The distinction is whether we LEARNED anything about the session. A refresh the backend REFUSED (auth-class) says the refresh token is dead too, so the original 401 is the honest answer and the caller may route to sign-out. A refresh that never got an answer — offline, DNS, a 5xx, a database outage behind the auth service — says nothing at all about the session, and reporting it as a 401 turned every such blip into a sign-out (the realtime supervisor and Session’s proactive refresh both classify Auth as fatal). Those propagate as themselves, which classify calls retryable — the same verdict the proactive-refresh task already reaches for a non-auth failure.

async fn post_file<T: DeserializeOwned>( &self, path: &str, bytes: Vec<u8>, mime: &Mime, ) -> Result<T>

POST one file as a multipart/form-data body with a single file part (the part name the upload routes look for), decoding the JSON response.

The part carries an explicit Content-Type: the server fast-paths on the DECLARED type and then verifies the bytes’ magic against it, so a part with no type is rejected as unsupported however valid the image is. bytes is moved, not borrowed — the retry seam rebuilds the request, so the body must be re-creatable from an owned buffer.

mime is a parsed Mime, not a string: a media type this layer would have to re-validate (and re-fail on) is a caller’s argument error, and taking the type makes it unrepresentable here.

pub async fn upload_accept_post( &self, purpose: UploadPurpose, ) -> Result<Vec<Mime>>

OPTIONS /upload/{avatar,attachment} — the image types this deployment will accept for that upload, read off the Accept-Post response header (the IANA-registered header a resource uses to advertise what it takes).

Asked rather than assumed because the answer moves with the server: JPEG XL support arrives by backend deploy, not by client release, and a client that hard-codes the list either offers a type the server rejects or hides one it accepts.

An unadvertised list is empty, not an error. A backend that answers the probe without the header (an older one) has told us nothing, and “nothing” is for the caller to interpret — it falls back to its own built-in set rather than blocking an upload on a missing advertisement. A transport failure or a non-2xx status still surfaces as HoundError, because those are failures.

GET /realtime/config — where the realtime plane is: a webtransport_url means “try WebTransport first”, its absence means “WebSocket only”; cert_hash is the digest to pin against a dev self-signed endpoint.

The realtime shell re-fetches this on EVERY connect attempt, not once at startup. Two reasons, both load-bearing: the advertisement can change under a redeploy, and going through this client is what rotates an expired access token (the 401 hook) — so the token read straight afterwards is current rather than the one captured at sign-in.
