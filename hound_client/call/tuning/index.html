hound_client::call

Module tuning 

Source
Expand description

Cross-module tuning constants — the call’s rates, geometries, cadences, track names and wire priorities — plus the broadcast-path scheme they attach to. One flat namespace of numbers so a change to the call’s shape is a one-file diff.

ADAPT_TICK_INTERVAL 🔒
Sender-side BWE/congestion adaptation tick cadence: one decision per second folds RTT + the worst receiver-reported loss into a target bitrate/rung the encode loop applies.

HEARTBEAT_INTERVAL 🔒
Heartbeat cadence (keeps the backend’s voice-membership alive).
MIC_BITRATE 🔒
Mic Opus bitrate. 48 kbps mono fullband VOIP is effectively transparent for speech — Discord’s 64 kbps default buys nothing audible over it on a mono mic track — while DTX + the publisher silence gate keep the idle cost near zero. Fixed for the call: audio is the “sacred” plane the send budget carves out first (adapt.rs), never the release valve; if audio ever must degrade under congestion, OpusEncoder::set_bitrate is the live lever (floor ~24 kbps).
MIC_TRACK 🔒
moq-net track names (one per source) under the per-peer broadcast path.
PLAYOUT_TARGET_US 🔒
Per-peer jitter-buffer depth floor the adaptive jitter grows from. 80 ms buys headroom so a brief fill-thread scheduling hiccup under heavy video load can’t drain the buffer before the next frame lands — defense in depth behind the RT audio runtime (which is what actually prevents starvation). The adaptive estimator still grows above this on a jittery link; the extra baseline latency is inaudible for conversation and buys a full Opus frame of slack.
SCREEN_AUDIO_BITRATE 🔒
App-audio Opus bitrate for a shared window’s audio. This is music/system audio, not a mic — encoded in OpusProfile::Music (general-audio) mode, so it needs a music-grade rate: speech-grade rates (~32 kbps) audibly crush music. 96 kbps mono is near-transparent for general audio.
SCREEN_AUDIO_TRACK 🔒
SCREEN_BITRATE 🔒
Screen publish bitrate seed — the initial encoder target before the BWE adaptation settles onto a ladder rung. Matches the 1080p30 SCREEN rung (~2.4 Mbps, see screen_bitrate_bps) — a screen-content target, NOT a camera-video one. A camera-grade seed (several Mbps) would saturate the shared QUIC connection before BWE reacts and starve audio/other video, while screen content (mostly static, text) looks crisp in H.265 at this rate. The BWE climbs from here if the link genuinely has headroom.
SCREEN_FIRST_FRAME_DEADLINE 🔒
How long a screen capture may run without EVER delivering a frame before the capture thread gives up and asks for a restart (policy::first_frame_overdue). A source that never produces frame #1 (Windows WGC can do this indefinitely) errs on nothing: no frames, no error, and the liveness probe still sees a live handle, so the loop would idle forever behind a black self-preview.
SCREEN_FPS 🔒
SCREEN_IDLE_POLL 🔒
Damage-driven screen capture: bounded wait for a frame (a static screen produces none) so the loop can re-emit a cached frame for new subscribers.
SCREEN_KEYFRAME_CADENCE 🔒
Screen keyframe cadence: IDRs on demand only (a subscriber’s RequestKeyframe — sent at subscribe and re-sent by the receiver’s awaiting-keyframe nag — or a PLI), plus a slow safety net. Screen content is mostly static, and a periodic IDR of an unchanged 1080p frame is pure redundancy — a short fixed cadence would dominate the data cost of a static share (hundreds of kbps for zero new information). max_gop_frames = 900: one GOP = one moq group, and moq-net evicts a group past 1024 objects (a fatal CacheFull for the drain) — 900 bounds the GOP safely under that cap even at sustained 60 fps (≈15 s), while the 60 s safety interval governs low-fps/static content (tiny groups).
SCREEN_MAX_H 🔒
SCREEN_MAX_W 🔒
Screen-share publish geometry: capture is native, scaled to this 1080p-class cap preserving aspect (text stays legible without 4K uplink cost).
SCREEN_RESIZE_DEBOUNCE 🔒
How long a changed window size must hold before the share restarts at the new geometry — one restart when a live drag-resize settles, not dozens.
SCREEN_RETRY_BACKOFF 🔒
Backoff the screen capture thread sleeps before signalling Retry after a transient capture error/panic — bounds the restart rate if the source keeps faulting immediately (the share restart itself paces it further).
SCREEN_STATIC_REFRESH 🔒
Re-emit the last screen frame at least this often (timestamp advanced) so a static share still delivers pixels to a freshly-subscribed peer.
