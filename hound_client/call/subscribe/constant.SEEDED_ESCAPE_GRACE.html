The bounded gate on escalating a tile to the SOURCE track. One per (peer, video source); pure, so the whole policy is unit-tested.

§What it fixes

pick_layer used to answer a capped demand with low.or(source), and a tile with no report yet defaulted to Source. At a 32-peer join neither the low decls nor the tile reports exist yet, so every receiver subscribed to 31 source tracks (~46 Mbps) and only walked back down a debounce later — a self-inflicted congestion collapse at exactly the moment the call is most fragile. Jitsi ships the same policy as a default (initial-max-height-px = 0: forward nothing until the receiver states its demand), and MoQT draft-19 names the shape RENDEZVOUS_TIMEOUT — “the duration the subscriber is willing to wait for a publisher to become available”.

§Why it cannot blank a legitimate tile

Three independent escapes, any one of which allows the source immediately:

  1. on_source — a tile already showing source video is never torn down to wait for anything. A shrink or a hide is a downgrade decision, made by the hysteresis, not by this gate;
  2. low_seen — once the _l0 decl has been in the roster for this (peer, source), its later absence is a real teardown (the resume-after-pause path, where the producer withdrew the decl while we were paused), not a join race. That case keeps its original instant fallback, guard tests and all;
  3. the grace itself — a producer that will never publish a low layer (an old peer, a failed low encoder, a lost request) is indistinguishable from a slow one, so the wait is bounded and then waived for good: the tile takes the source and never pays the wait again on this establish. Without the latch a peer that never publishes low would re-pay it on every resubscribe, and the resume-after-pause budget would be a grace longer for no benefit.

§Who still reaches the demand_known: false branch

In the shipped app, essentially nobody past the first tile that lays out: TileDemand seeds every roster peer’s silence to Hidden once this receiver has reported anything at all, so a tile the virtualized grid never BUILDS is treated as not-rendered rather than as unknown. The branch is kept because it is the honest answer for a receiver that reports no demand at all — houndbot, the testkit harness, any future surface that renders video without a layout pass — which must still get video, and gets it one grace after joining.

§Interaction with the receive-side budget

The waiver outranks the budget, and deliberately. hound_media::allocate_video can hand a tile the thumbnail rung and this gate can still put it on the SOURCE track a grace later, because the alternative — holding a capped subscription against a producer that never published _l0 — is a permanently blank tile, and P2 already decided a blank tile is worse than an expensive one. The budget is not undermined by that: it bounds what this receiver ASKS the producers for, the waiver is a last-resort escape from asking for something nobody publishes, and the escape shows up honestly in the controller’s own accounting — the apply pass prices the track actually subscribed to, so a waived tile is billed at the source rate it really costs and the budget backs off accordingly.

How long a tile whose demand is only INFERRED — this receiver reports, but has never reported this tile — stays unsubscribed before it escalates to the thumbnail rung. See TileDemand’s two-tier trust model: a reported hide is trusted forever; an inferred one is not, because a lost report and a tile the grid never built look identical from here.

10 s is long enough that the UI’s own recovery (a re-assert on connect or roster change, demandNeedsReassert) always wins the race in a healthy app, so this never fires for a tile that is genuinely off screen — and short enough that a user staring at a black tile because their report was swallowed gets video back before they reach for reload.
