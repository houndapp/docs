Module video_rx 

Source
Expand description

Inbound video: the async pull half (receive-side keyframe gate; the nag task lives with the subscribe loop) feeds a blocking decode thread that owns the !Send VideoDecoder and rebuilds it whenever the sender’s per-packet codec byte changes — the sender’s choice drives decode. Decoded frames pass through a shallow playout stage (VIDEO_PLAYOUT_DELAY_US) that replays the sender’s frame spacing, then reach the sink surface-first (zero-copy GPU handle) with materialized I420 as the universal fallback; push_preview is the borrow-based capture-side twin the publish loops use for self-preview.

The playout stage is presentation pacing only — it does NOT anchor video against the audio plane’s own (adaptive, deeper) jitter depth, so the two planes are still independently scheduled.

DecodeFailures 🔒
Pure consecutive-decode-failure policy. A decode error is NOT a construction error: the usual cause is a missing reference, which the decoders heal from on the next keyframe by themselves (VideoToolbox rebuilds its session on new SPS/PPS, openh264 absorbs in-band parameter sets) — so the loop KEEPS the decoder and only signals the pull half to request one. Tearing down per failure instead re-ran Engine::new().video_decoder(..) (a full VAAPI/openh264 setup) and an info! at the arrival frame rate — the very storm RETRY_AFTER exists to bound, reached through the decode door.
DecoderRetry 🔒
Pure decoder-(re)build retry policy (see RETRY_AFTER). Consulted before every Engine::new().video_decoder(..) call for a codec whose current decoder doesn’t match. Takes now as a parameter so it is unit-testable without a live clock.

Constants§

FIRST_KEYFRAME_DEADLINE 🔒
How long a fresh video subscription may sit with nothing DECODED before the pipeline ends itself so the reconcile re-subscribes (restart-ladder paced). Past the nag window (5 × 2 s): a producer that ignored every re-request is wedged or its broadcast is a zombie from a same-path replacement, and only a fresh subscribe — a new announce cursor + control-plane Subscribe — heals those; waiting on the 60 s safety-net IDR is a frozen tile.
RETRY_AFTER 🔒
How long the decode loop withholds retrying platform-decoder construction for a codec that just failed to build. Without this, the per-packet wire codec byte is sender-controlled — a peer sending AV1 to a box with no AV1 decode makes every single frame re-attempt Engine::new().video_decoder(..) (a VideoToolbox/VAAPI session setup) and warn!, forever. That is a remotely triggerable retry storm (CPU burn + log spam) for the lifetime of the subscription.
VIDEO_PLAYOUT_DELAY_US 🔒
How long a decoded frame waits in the playout buffer before it reaches the renderer. Deliberately SHALLOW — between one and two 30 fps frame intervals — because this stage buys presentation pacing, not loss recovery: frames arrive and decode in bursts (a group flush, a retransmit tail, a slow software decode), and rendering them the instant they pop out plays a nominally-30 fps tile as judder. Scheduling each frame against the sender’s capture clock replays the sender’s spacing instead.
VIDEO_PLAYOUT_MAX_FRAMES 🔒
Bound on decoded frames held for playout. A decoded frame can hold a GPU surface lease (a VideoToolbox IOSurface, a D3D11 texture-pool slot), so the depth must stay well inside a decoder’s pool: 8 is several times the steady-state occupancy (1–2 frames at the shallow target) and only reachable when the pump is already hundreds of ms behind, where drop-oldest is the right answer for video anyway.
VIDEO_STALL 🔒
How long the video pull tolerates delivering NOTHING before treating the subscription as stalled. Above the static-share re-emit cadence (SCREEN_STATIC_REFRESH, 1 s) so a healthy static share never trips it; a mid-GOP loss stall or a silent producer does within seconds instead of a retransmit tail.
VIDEO_STAMP_RUN 🔒
Consecutive strictly-advancing wire timestamps that turn playout scheduling on (or, in the other direction, non-advancing ones that latch it off) — see PlayoutMode. Three frames is ~100 ms of stream: long enough not to judge a sender on one duplicate stamp, short enough that pacing engages immediately.

Functions§

push_decoded 🔒
Hand one DECODED frame to the render sink, surface-first (zero-copy GPU handle) with materialized I420 as the universal fallback. Consumes the frame, so the no-surface case MOVES the decoder’s conversion buffer instead of copying ~1.4 MB per frame per peer (push_preview is the borrow-based capture-side twin).
push_preview 🔒
Push one CAPTURED frame to the render sink for a self-preview tile, preferring the ZERO-COPY surface path: a surface-backed frame (SCK / AVFoundation NV12 IOSurface) is handed to the renderer to sample directly — no NV12→I420 CPU conversion, no ~1.4–3 MB per-frame alloc+copy, no re-upload (~90 MB/s of conversion at a 1080p 30 fps share). Falls back to materialized I420 for non-surface frames (scaled camera frames, other platforms) or a sink without a surface renderer. Borrows the frame — the caller still owns it for encode. (The REMOTE decode path keeps its own ownership-optimized version of this pattern: it consumes the frame, so its no-surface case can MOVE the bytes instead of copying.)
video_decode_loop 🔒
The blocking video decode loop: owns the !Send VideoDecoder, rebuilds it when the sender’s codec changes (the sender’s choice drives decode), and pushes each decoded frame to the sink through a shallow playout stage (VIDEO_PLAYOUT_DELAY_US) that replays the sender’s frame spacing. A decode failure — and a decoder that will not BUILD — raises resync_needed, this thread’s only route to the control plane (see DecodeFailures).
video_pipeline 🔒
Video decode pipeline. The MoQ subscriber pull is async (must run on the runtime), but the engine VideoDecoder (VideoToolbox/dav1d) is !Send, so it CANNOT live across an .await. The async half therefore only PULLS frames — applying the receive-side keyframe gate so we never feed a delta before the first keyframe — and forwards them to a dedicated blocking decode thread that owns the !Send decoder and pushes decoded I420 to the sink keyed by peer.
