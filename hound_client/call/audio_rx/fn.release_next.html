The hold’s release decision — the whole of it, so the pull loop below is only network I/O and the policy can be driven by tests against the real jitter machinery. Returns the frame to process now, or None meaning “pull more”.

Three rules, in order:

  1. The suppression drain. drain is set when a DTX-sized frame arrives, which is the sender telling us it has stopped transmitting: the next frame is a keepalive interval (~500 ms) away, so there is nothing left to reorder against and every frame still held is waiting on a network event that will not come for half a second. Empty the hold, then clear the flag and resume normally.

    Holding through suppression is not merely late, it corrupts the receive-side estimates. The hold releases by COUNT, so each keepalive would be handed on one arrival later — ~1.5 s behind the wire — and every push would then land past its scheduled playout (a run of overdue arrivals → shallow re-anchors), while the 500 ms release cadence would read as transit deviation and pin the recommended depth at its cap for the whole peak window.

    What the drain gives up is reorder protection for the frames it releases early. That is the right trade and a small one: the frames in question are the tail of the confirmation window and the keepalives themselves — silence — and past the first keepalive the stream is 500 ms/frame, which no reordering reaches across. Speech is never drained early, because a coded frame never arms the flag.

  2. Steady state. Release the oldest once more than AUDIO_REORDER_HOLD are buffered, so network reordering is undone before the stateful decode.

  3. End of track. Drain whatever remains, oldest-first.

All three are arrival-driven, never timed: the moq group read is not cancel-safe mid-object, so nothing may be raced against next_frame.
