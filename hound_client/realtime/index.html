The realtime plane: the IO shell around [hound_realtime::ClientSession].

All protocol logic — the Hello→Welcome handshake, the desired-vs-issued subscription reconciliation that survives a reconnect, the frame→event mapping — lives in the sans-IO reducer. This module only moves bytes: it picks a transport, drives one [MessagePipe], and translates the reducer’s [Action]s and [Event]s into wire frames and a typed RealtimeEvent stream.

§Two legs, one loop

Per attempt the shell asks the backend where the realtime plane is (GET /realtime/config) and tries WebTransport first when a URL is advertised, falling back to a plain WebSocket in the SAME attempt. Both legs are [MessagePipe]s, so run_session is written once and instantiated twice. The credential travels in an Authorization: Bearer header on both legs — never in a URL, which every proxy and access log between here and the backend would keep.

§Where an auth verdict may come from

Only two places: a WebSocket handshake refused 401/403, and an Auth error from GET /realtime/config (which is trustworthy because it has already survived the REST layer’s refresh-and-retry — see RestClient’s 401 hook). Everything else is retried, including a WebTransport [WtError::Rejected]: wtransport reports SessionRejected for any non-2xx answer to the CONNECT and for a CONNECT stream stopped mid-handshake, which is what a pod rollout and a misrouted host both look like. Treating that as an answer signed users out over a deploy; it is now a fallback to the WebSocket leg in the same attempt.

§The supervisor

RealtimeClient::connect tries the first session inline (so a reachable backend is welcomed before the caller proceeds) and then hands it to a supervisor task that owns it. A first attempt that FAILS is not an error to the caller: it is logged and the supervisor retries, because a sign-in must not fail on a realtime plane that is merely down. The supervisor holds the [ClientSession] — no lock anywhere, because exactly one task touches it — and reconnects forever under the CALL plane’s ladder (crate::call::reconnect::Backoff: 500ms→15s ±20% jitter, re-armed only by a session that lived ≥30s). The invariants it exists to hold:

  • Never strand a stale JWT. Every attempt re-reads the token out of session state (through RestClient, whose 401 hook rotates it), so a reconnect after an hour offline presents a live credential rather than the one captured at sign-in.
  • Only an auth refusal is fatal. A WS 401/403 or an Auth error from the config fetch ends the supervisor and emits RealtimeEvent::AuthExpired.
  • A version mismatch is terminal too, but is NOT an auth outcome: the build cannot talk to this server, so the supervisor stops and emits RealtimeEvent::VersionMismatch rather than storming the backend with a handshake it will refuse identically forever.

UNAVAILABLE_RETRY 🔒
Delay before the one in-session retry an ErrorCode::Unavailable earns. The server could not reach the state to decide (a database blip), so the subscription is neither issued nor refused — asking again shortly is the whole recovery.
WELCOME_DEADLINE 🔒
How long a session may sit unwelcomed after the transport is up. The backend closes a connection that has not said Hello within 10s; ours must be at least that (we are the ones who send it) plus room for the round trip, and anything past it is a peer that accepted a socket and then stopped progressing.
WS_CONNECT_TIMEOUT 🔒
How long the WebSocket leg’s dial (TCP + TLS + upgrade) may take. Mirrors RestClient’s connect timeout and its rationale verbatim: a half-dead server (TCP accepted, upstream never answers — a churning ingress does exactly this) hangs every caller forever, and here “every caller” is the supervisor’s ladder, which would stop retrying while it waits.
WS_KEEPALIVE 🔒
Idle period after which the WebSocket leg sends a Ping. A quiet realtime connection sends nothing for minutes and NAT/proxy idle timeouts kill it; the WebTransport leg needs no equivalent because QUIC keep-alive is configured on the endpoint ([ClientOptions::keep_alive]).
WS_SILENCE_LIMIT 🔒
How long the WebSocket leg tolerates hearing nothing at all — not one frame, not one Pong — before declaring the peer gone.
WT_CONNECT_TIMEOUT 🔒
How long one WebTransport dial may take before the shell gives up and falls back to the WebSocket leg in the same attempt. Short on purpose: a blocked UDP path (a corporate firewall, a NAT that drops QUIC) fails by timing out, and the user must not wait out a transport-level timeout to reach a plane the WebSocket serves fine.
WT_FAILURE_STREAK 🔒
Consecutive WebTransport dial failures after which the shell stops trying it. On a network that blocks UDP outright, every reconnect otherwise pays WT_CONNECT_TIMEOUT before reaching the leg that works.
WT_RETRY_AFTER 🔒
How long the WebTransport leg stays skipped once the streak trips. A client moves between networks without restarting, so the skip must expire.
WT_STREAM_TIMEOUT 🔒
How long opening the WebTransport control stream may take. A session that handshakes and then never gives us a stream is indistinguishable from a wedge and would otherwise park this attempt forever — the same reason the backend bounds its accept.
