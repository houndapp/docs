Expand description

The camera and screen send sections carry the same signals under two struct types (screen has no pli_received, camera no audio_send_kbps). Normalizing them into one view is what lets every send rule be written once and applied to both — and it is where the ONE real difference between them lives (SendView::static_dedup).

§remote_loss_pct: f64§target_kbps: f64§rung: &'a str§codec: &'a str§width: u32§height: u32§publish_live: bool

Whether a receiver is attached. While DARK the capture thread deliberately encodes nothing — capture keeps running so self-preview never freezes — so an encoded rate of 0 against a full-rate capture is the DESIGNED state. Every capture/encode rule is gated on this exactly the way it is gated on the pause.

§static_dedup: bool

Screen capture only counts REAL frames: a static share stops capturing entirely while the encoder keeps re-emitting the cached frame at ~1 Hz. So a stalled capture is only a fault here if the encode side went quiet too, and the capture-vs-rung keep-up rule cannot apply at all.

fn paused(&self) -> bool

Congestion has paused this track’s video. Every capture/encode rule is inert while paused — silence is the intended behaviour, not a fault.

Source

fn dark(&self) -> bool

Publishing with nobody subscribed. The publish loop’s live gate is still shut, so the capture thread skips encode entirely (nobody encodes into the void) while capture keeps running for the self-preview tile. A HEALTHY idle state — the report says so on an info line rather than diagnosing it.

Source

fn encoding_expected(&self) -> bool

Whether this track’s capture/encode stages can be judged at all. The two idle states are indistinguishable from a dead pipeline on the counters alone — full-rate capture, zero encode — so both have to gate the rules, or a lone participant with nobody watching is diagnosed with a dead encoder every second (and the sustained-degradation latch WARNs about it once per dark period).

Source

fn rung_fps(&self) -> Option<f64>

The rung’s negotiated frame rate, parsed from the adaptation tick’s label ("{w}x{h}@{fps}"). None before the first tick (empty label) or while paused — the keep-up rules then simply don’t apply.

Source

fn expected_encode_fps(&self) -> f64

What the encoder SHOULD be emitting: it can’t encode frames capture never produced, and it deliberately won’t exceed the rung’s fps cap.

Source

fn capture_stalled(&self) -> bool

The source has stopped delivering. For a screen share the encode side must be quiet too, otherwise this is just static content (see Self::static_dedup).

Source

fn capture_slow(&self) -> bool

The source is delivering, but well under the rate that was negotiated.

Source

fn encode_stalled(&self) -> bool

Frames go in, access units don’t come out.

Source

fn encode_slow(&self) -> bool

One encode call is eating the frame budget.

Source

fn publish_backpressure(&self) -> bool

Encoded AUs can’t get onto the wire fast enough.

Source

fn uplink_loss(&self) -> bool

Receivers are losing what we send (loss reports, or a storm of keyframe begging).
